# 01: Address the non-blocking suggestions left open by feature 0002's reviews

**What to build:** feature 0002-router-reliability's three tickets were all approved with zero blocking or important findings, but their reviews left seven `suggestion`-severity items on record, accepted and logged rather than fixed at the time. Clear all seven now.

**Blocked by:** None (can start immediately).

**Spec:** none (fast path). The checklist below is normative.

- [x] `model_router/provider.py`: `is_retryable`'s docstring restates the function name (adds nothing the signature doesn't already say). Drop it, or replace it with the one non-obvious fact - that an unrecognised exception type defaults to not-retryable on purpose. (From ticket 01's review.)
- [x] Unify the clock-seam patching style across the test suite: `tests/test_call_log.py` patches `model_router.router._sleep` by string, `tests/test_routing.py` patches the `router` object's `_sleep` attribute directly. Pick one form, apply it everywhere the seam is patched. (From ticket 01's review.)
- [x] `model_router/router.py` `_attempt_tier()`: the retryable/exhausted decision is expressed twice - the loop's `break` condition (`if error is None or not is_retryable(exc): break`) and the separate post-loop `exhausted = error is not None and is_retryable(exc)` line, five lines apart. Derive `exhausted` from the loop's own exit condition instead, so the rule has one statement and a future change to one can't silently diverge from the other. (From ticket 02's review, round 2.)
- [x] A mixed chain - two or more retryable failures followed by a non-retryable one at the same Complexity Tier - correctly terminates `route()` at that tier without escalating, but nothing pins this: add a test driving that exact sequence (e.g. `[503, 503, 400]` at the Classifier's tier) and asserting no request reaches the next tier. Add one README clause noting that a permanent failure ends the task at the tier where it occurred rather than escalating, since the current "When a Complexity Tier's Attempts are exhausted, the task escalates" phrasing reads ambiguously for this case. (From ticket 02's review, round 2.)
- [x] `model_router/router.py` (~line 51): the post-loop `return RouteResult(tier=tier, model=model, answer=answer, error=error)` for the top-tier-exhausted path still reads the `for` loop's leaked variables - correct only because `ladder_from()` is provably non-empty, unguarded. Return that result from inside the loop under the existing top-tier branch instead, so the function has no post-loop dependence on loop variables. (From ticket 03's review.)
- [x] `model_router/budget.py` `load()`: `ROUTER_BUDGET_USD=nan` or `=inf` currently passes startup validation (`limit <= 0` is `False` for both) and produces a guardrail that silently always-blocks (`nan`) or never-blocks (`inf`) escalation for the whole session - the same silent-behavior-change failure mode the existing invalid-value check exists to catch. Reject non-finite values (e.g. `not math.isfinite(limit)`) alongside the existing `<= 0` check. Extend the existing parametrized invalid-value test in `tests/test_budget.py` with `"nan"` and `"inf"` cases. (From ticket 03's review.)
- [x] Add a `run_repl`-level test that drives cross-task Budget Guardrail accumulation through two tasks in one `run_repl` session (not just direct `route()` calls sharing a guardrail object), asserting the session-spanning object is honored at the REPL entry point rather than only at the `router.route()` level. (From ticket 03's review.)
