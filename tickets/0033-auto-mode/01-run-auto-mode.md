# 01: Run ordinary Tools automatically while retaining Strong Confirmation

**What to build:** The user opts into a third Run-local Agent Mode, `auto`, to execute build-available ordinary Tools without answering repetitive prompts; matched Dangerous Commands still require the existing Strong Confirmation, and plan/build retain their current behavior. A complete slice from mode selection through model-visible Tools and real execution to results and Call Log.

**Blocked by:** None (can start immediately).

**Spec:** `docs/specs/0033-auto-mode.md` (R1–R6, Implementation/Testing Decisions); **ADRs:** ADR-0004 (Input Box), ADR-0005 (Resume and Call Log).

- [x] `/mode auto` selects the mode for later routed turns; `/mode` reports it. Invalid/extra arguments keep the prior mode and show usage locally, `/help` and interactive completion disclose auto, `/model auto` remains a separate Tier Pin command. Fresh and Resumed Runs start in build; Shift+Tab cycles `plan → build → auto → plan` while editing without submitting/altering the draft and not during Tool Confirmation. Footer and piped replies show the selected mode as appropriate; mode commands cause no Provider Attempt.
- [x] In auto, the Router offers the same registered Tool names/schemas as build (including shell/websearch opt-outs) across retries, Escalation and follow-up Tool rounds, with mode-accurate System Prompt and Tool descriptions. Switching modes affects only later routed turns including `/retry`/Continuation Turn; tier routing, Conversation, Todo List, active Skills and Tool-free Compression remain unaffected. Plan still refuses Mutating Tools before validation and keeps Network Tool Confirmation.
- [x] Tool Registry auto-executes only after normal schema validation and successful preparation for unflagged `shell`, `write`, `edit`, `apply_patch`, `webfetch`, and registered `websearch`. In both interactive and piped input, these calls need no approval input and emit no confirmation preview, question or warning; the usual Tool result, errors and Call Log records still occur. Confirm that path and file limits, preparation failures, redaction and Workspace Root checks still hold; `question` still collects actual answers interactively and does not treat auto as a response.
- [x] A prepared shell command with existing non-empty `dangerous_rules` still uses the normal Strong Confirmation preview showing the exact command, matched rules and any fetched-content warning from preceding successful `webfetch`/`websearch`, including same-batch calls. `yes` (case/whitespace tolerant) approves; `y`, EOF or other input rejects without running, Ctrl-C interrupts, and approved/rejected Call Log entries keep matched rules. A subsequent unflagged command after external content still skips preview. Do not change the detection rules. Build keeps ordinary/Strong Confirmation and warnings; plan keeps its old gate.
- [x] Offline scripted REPL plus fake Provider tests cover all paths above with interactive Input Box and piped input, using harmless flagged commands only (e.g. `eval touch marker.txt`); assert Provider Tools/prompt, actual effects, no extra input consumed, user output, ordinary/dangerous Tool results and Call Log. Reuse `tests/test_repl.py`, `tests/test_input_box.py`, `tests/test_routing.py`, and existing Tool tests, stub network with local fakes; run the full offline test suite. Do not introduce a new Tool, Provider change, persistence, sandbox or Dangerous Command rule.
