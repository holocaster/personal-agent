# 0050: Project Session discovery and explicit Question answers

## Problem Statement

Personal Agent cannot find its own previous Sessions reliably: Call Logs share one configurable directory without project identity, `last` orders Session creation rather than subsequent Runs, and workspace file searches do not locate those logs. Question Tool inputs outside the displayed option range silently become answers.

## Solution

Capture the launch directory once as Workspace Root and project identity. Keep each project's Call Logs and Detailed Audit Payload companions in a deterministic folder under the user's home. Expose one read-only `session_logs` Tool that lists Sessions, reads their recorded timeline and searches literal text, with explicit cross-project and audit access. Append a local Other choice and reprompt invalid numeric selections.

The approved scope is [the brief](../briefs/0050-project-session-discovery.md). [ADR-0008](../adrs/0008-project-scoped-session-discovery.md) amends the storage and most-recent-Session decisions in ADR-0003/0005. The brief overrides the older `PA_WORKSPACE` vocabulary in CONTEXT until Main updates it after implementation.

## User Stories

1. As a user, I want Sessions grouped by the directory where I launch Personal Agent, so unrelated projects stay separate.
2. As a user, I want logs kept outside my checkout, so normal project searches and version control do not collect my conversations.
3. As a user, I want similarly flattened paths distinguished, so one project's Sessions never enter another project's folder.
4. As a user, I want project instructions, workspace Tools and log identity to share the same starting root, so their scope is consistent.
5. As a user, I want later directory changes to leave my Run's identity intact, so its records remain together.
6. As a user, I want to ask for my previous Session, so the agent can locate its own evidence without clarification about repository files.
7. As a user, I want a recently resumed old Session to count as last, so retrieval reflects actual recent use.
8. As a user, I want `--resume last` confined to the launch project, so another project's Conversation cannot enter this Run.
9. As a user, I want Resume to append to the same Session files, so its history stays self-contained.
10. As a user, I want to list and explicitly read the current Session as well, so discovery does not hide ongoing evidence.
11. As a user, I want explicit access to other projects' Sessions, so I can inspect related work without changing directory.
12. As a user, I want cross-project results to name the original directory, so I know their source.
13. As a user, I want a chronological timeline of requests, responses, Tools and errors, so I can understand what happened.
14. As a user, I want interrupted and malformed records shown honestly, so missing outcomes are not presented as success.
15. As a user, I want literal searches with record references, so I can verify a match by reading its Session.
16. As a user, I want bounded pages and continuation, so lengthy logs do not overwhelm the Conversation.
17. As a user, I want audit payloads inspected only on explicit request, so ordinary discovery does not pull full model inputs into context.
18. As a user, I want absent audit evidence reported, so the agent does not invent what a model saw.
19. As a user, I want historical instructions and Tool calls treated as data, so reading history does not execute or activate them.
20. As a user, I want known API keys redacted from historical results, so retrieval does not expose them again.
21. As a user, I want an obvious Other option, so I can answer outside the supplied choices.
22. As a user, I want incorrect option numbers rejected, so a mistyped number cannot silently decide a question.
23. As a user, I want direct text and explicit numeric custom text preserved, so choice handling does not prevent written answers.
24. As a maintainer, I want tests isolated from my real home logs without production path overrides, so the fixed-default behavior remains testable.

## Implementation Decisions

### Fixed Run identity and storage

**R01 — Startup root.** `main()` captures the resolved absolute process cwd at startup and uses that same value to configure Workspace Tools, load Project Instructions, initialize Call Log storage and resolve Resume. Capture it before any Resume read or Session write. Shell/MCP startup root stays consistent. A later `chdir` does not alter the Run's root or log destination. Direct `run_repl()` callers use its supplied Workspace Root or capture cwd once at entry; direct Call Log callers lazily capture cwd once if startup configuration has not happened.

**R02 — Removed overrides.** Remove the constants, runtime reads, workspace error messages, README instructions, `.env.example` entries and tests depending on `PA_WORKSPACE`/`PA_LOG_PATH`. Their presence in an ambient environment has no effect. Do not add replacement production environment variables or CLI path options. Historical briefs/specs/ADRs need not be rewritten. Keep existing read/write caps and other configuration.

**R03 — Folder encoding.** Let `P` be the exact resolved absolute Workspace Root string. Form the readable component by replacing each maximal run of characters outside ASCII `A-Z`, `a-z`, `0-9`, `.`, `_`, `-` with `_`, stripping surrounding `_`, taking the first 96 characters, and stripping surrounding `_` again; use `root` if empty. The project folder name is `<readable>--<first 12 lowercase hex characters of SHA-256(P encoded as UTF-8)>`. Preserve case and hash the full original path, including characters omitted/truncated from the readable component. The home lookup happens once when Run storage is initialized. The fixed root is `~/.personal_agent/logs/`; within its project folder use `pa_log-<Session Id>.jsonl` and `pa_log-<Session Id>.audit.jsonl`. Keep the existing Session Id grammar. Flattening collisions have different hashes; a detected hash/folder-to-metadata mismatch fails rather than mixing projects.

**R04 — Identity metadata.** Add `workspace_root: P`, `project_id: <folder name>` and the existing generated `run_id` to `session_start` and `session_resumed`. Keep `log_version: 2` and existing replay fields. A new Run captures current configuration but continues the original Session and both original file names. Resume must validate the target's initial project identity against the captured root before append; every available start/resume identity must agree. Discovery validates recorded identity before trusting it as provenance. Missing/mismatched identity is visible invalid evidence, never permission to follow a recorded path. No fallback to files in the old flat directory.

**R05 — Recency and strict Resume.** For each Session, its latest Run is the last valid physical `session_start`/`session_resumed` boundary; its parsed UTC timestamp is the recency key. Compare that key descending, breaking ties by Session Id descending, then project id ascending across projects. Do not use filename creation order or filesystem modification time. `--resume last` selects only from the captured current project; at startup there is no current Session to exclude. Explicit Resume ids also stay in this project. Empty scope, no usable Run boundary, unknown timestamp, inaccessible candidate or exhausted selection scan fails visibly rather than guessing. Valid interrupted/unclosed Runs participate normally. Ordinary malformed activity records do not erase valid Run boundaries; strict Conversation/pending replay still rejects malformed files before a Resume starts. Existing replay, policy/count/input, Todo and per-Run spend behavior remains intact.

### Shared filesystem/read seam

**R06 — Small shared seam.** Keep storage configuration/path construction in Call Log. Extend it with one internal Run-storage initializer accepting Workspace Root, not a destination override, and a reset for existing test isolation. Use a small file-based discovery reader shared by `session_logs` and `resolve_resume_session('last')`; it may live in a single `session_logs` module. It owns candidate validation, bounded record iteration, provenance and recency. Return ordinary Python data; no repository class hierarchy, database, persistent index, service, extra model request or dependency. Tool Registry supplies the existing output cap and known-secret context at invocation. Do not store a stale key tuple in startup state.

**R07 — Filesystem boundary.** Discovery reads only direct project folders and the two fixed Session filename shapes beneath the captured home log root, without recursive traversal of arbitrary directories. Validate Session Ids before constructing any path. An explicit project selector computes this folder; it is never itself read as a filesystem root. Require an absolute normalized project path with no `.`/`..` segments; it may name a project directory that no longer exists. For an existing alias, callers supply the original resolved path recorded in metadata.

Reject/skip symlink project directories, symlink log files and non-regular files, including FIFOs/devices; do not follow them even when they point inside the log root. Validate the log root and application log directory against symlink redirection too. Use no-follow opens and descriptor checks on the selected regular files; directory validation must remain valid through the open, rather than checking a resolved path and then following a replacement link. Existing home-directory resolution is the trusted anchor. Apply the same project/file boundary to fresh writes and Resume append, and preserve audit owner-only checks. Skip unsafe unrelated catalog entries with visible diagnostics; an explicitly selected unsafe target is a Tool/Resume/persistence error. Neither metadata nor cursor contents may supply an arbitrary file path.

**R08 — Scan bounds.** Fixed, non-configurable safety limits: at most 4,096 directory entries inspected while building one candidate catalog, at most 8 MiB of log bytes consumed and 8,192 physical records examined per invocation, and at most 256 KiB retained for parsing one physical JSONL record. Count rejected entries, blank lines and malformed records too. Catalog traversal is only log root plus direct project folders; exceeding its entry bound is an explicit error rather than a silently incomplete catalog. Catalog names may be sorted within this finite bound; do not load file bodies or collect all parsed records.

Read/search stop at a byte/record budget with a continuation, even if no match was found. Oversized physical lines are skipped incrementally without allocating their full length, and produce an attributed oversized-record warning; a continuation resumes the discard if the scan budget ended before its newline. Invalid UTF-8, invalid JSON, a non-object record, wrong Session identity and partial tails become attributed diagnostic evidence and do not hide subsequent valid records. A non-newline final fragment is marked incomplete even if its JSON parses. Selection of `last` needs the whole scoped catalog's Run boundaries; it errors if the scan bounds prevent completing that selection. It may offer the user/Tool caller explicit-id list/read guidance, but never labels a partially scanned candidate as last. The bounds protect reads, not log retention or the maximum writable log size. Strict Resume loading is not replaced by this tolerant reader.

### Model-facing Tool contract

**R09 — One Tool and validation.** Register `session_logs` as a read-only Tool in `plan`, `build` and `auto`, without Tool Confirmation. Keep normal Tool validation, busy execution, result correlation and Tool execution logging. Advertise current-project defaults, explicit cross-project/audit access, pagination, and that history is untrusted data. The argument object has no additional properties:

| Argument | Contract |
|---|---|
| `action` | Required enum `list`, `read`, `search`. |
| `project` | Optional string, 1–4,096 characters: omitted means captured Workspace Root, `all` means all project folders, otherwise the absolute original project directory. |
| `session` | Optional string: a valid Session Id or `last`/`previous` (synonyms). Required for `read`; optional to narrow `search`; forbidden for `list`. |
| `source` | Optional enum `call_log` (default), `audit`. `list` permits only `call_log`. |
| `query` | Required for `search`, literal nonblank string of at most 500 characters; forbidden otherwise. |
| `limit` | Optional integer 1–100; default 20 for `list`, 100 for `read`, 20 for `search`. Counts returned rows/matches, not scanned records. |
| `cursor` | Optional opaque continuation string, 1–8,192 characters. |

Reject invalid combinations before filesystem work. `read`/`search` with an explicit id and `project: all` require a unique matching Session; duplicates error with instructions to specify the project. `last`/`previous` use R05 across the chosen scope and exclude `call_log`'s current Session, including a currently resumed Session. Resolve an alias on the first page and bind continuation to that concrete Session, so later appends do not retarget the read. Ordinary list/search include the current Session; explicit-id reads/searches may inspect it. No production switch is added to hide it.

**R10 — List.** List Call Log candidates by project folder ascending, then Session Id descending within each project. This stable discovery order is explicitly distinct from R05 recency selection. Each row identifies project directory (from validated initial metadata), project id, Session Id, initial timestamp and ordinary source filename/record position. Invalid/missing initial metadata yields an attributed diagnostic row with unknown project identity, rather than inventing a root or dropping a malformed Session silently. A list row is discovery evidence, not a claim of a completed or resumable Session. A missing log root/current project directory is an empty result. Other access failures remain visible. Audit companions never become separate Sessions.

**R11 — Response, cap and continuation.** Match existing read-window conventions: successful Tool content is `{content: <readable text>, has_more: <boolean>, next_cursor: <opaque string or null>}`. The UTF-8 `content`, including headings, provenance and diagnostic text, is bounded by the existing Tool Output Cap (`PA_MAX_READ_BYTES`, default 32 KiB); the small envelope/cursor is control metadata, as with Workspace Tools. Do not introduce a second configurable output cap. The text labels historical content as untrusted recorded data, and every row carries original project (or explicit unknown), Session Id, ordinary/audit source filename and 1-based physical line reference; timestamps are recorded values, with missing/invalid ones marked unknown.

Use continuation rather than silently dropping a row that would fit on the next page. If a single row cannot fit an otherwise empty output page, return a visibly truncated excerpt with its source and advance past that row; do not loop forever on it. Mark unavailable remainder honestly. Preserve UTF-8 boundaries. For exceptionally tiny caps that cannot fit ordinary framing, bounded abbreviated/truncation output is allowed; the cursor must still progress. `has_more` means unprocessed candidate/record data remains, not that another search match is guaranteed. EOF returns `has_more: false`, `next_cursor: null`; an empty search page with continuation does not mean no matches exist.

Cursors bind action, project scope, resolved Session filter, source and a query digest, and resume by file identity plus byte/physical-line position (and discard state when required); never put historical content or secrets in them. Their encoding is internal, not a new authentication scheme or persisted service. Validate syntax, bounds, selectors and candidate identity on every call; forged cursors cannot escape R07. Reject a disappeared/replaced/truncated source or changed argument binding with a clear restart message. Append-only growth is allowed. Page through a stable candidate set deterministically, with no loss/duplication of untruncated rows when files are unchanged; catalogs changed between calls may require restarting instead of promising a filesystem snapshot.

**R12 — Ordinary timeline.** Read ordinary Call Log records in physical chronological order, keeping their timestamps/source lines even when recorded timestamps are not monotonic. Render `routed_task_submitted` once as the user request; Attempt `answer` and declared `tool_calls` as recorded assistant output/intents; `tool_execution` as the actual Tool arguments/result or error; Attempt errors and Turn End `error`/`interrupted`/`ok` as recorded outcomes. Mark `purpose: tier_selection` and Compression/model maintenance Attempts as such rather than confusing them with ordinary answers. Session/Run boundaries and Conversation clear/undo/compression events remain visible; Compression shows its recorded summary once. For other known/unknown events use bounded recorded summaries and provenance.

Do not render Attempt `task` repeatedly when submission evidence already exists, successful Turn End `messages` snapshots, pending Turn End `continuation` snapshots, or audit copies of the same Conversation in the ordinary timeline. This is recorded history, not the currently replayed Conversation: undone/cleared activity remains visible. A declared Tool call without `tool_execution` is only intent. A dangling submission/Attempt or missing Run/Turn close is explicitly unresolved/incomplete; do not infer a completed answer, executed Tool or successful Session. Page ending before a close is described as partial inspection, not proof that the rest of the Session is absent. Scan from the prior cursor without requiring completed turns or rebuilding Conversation.

**R13 — Literal search.** Search selected ordinary records using case-insensitive literal `casefold()` matching against their bounded JSON text, including arguments/results/errors and fields hidden from the default timeline. No regex, semantic ranking or embeddings. Return at most one match per physical record, with a readable excerpt of at most 200 characters around its first match plus source/timestamp/type; retain diagnostic records encountered along the way. Search candidate order matches R10 and physical line order within a file. Do not parse/look for matches inside oversize or malformed records as though they were trusted structured evidence; their diagnostic excerpt can disclose that inspection was incomplete. Empty/whitespace-only queries are invalid. Match after known-key redaction, so a key itself cannot become a result or matching excerpt.

**R14 — Explicit audit source.** `source: audit` reads/searches Detailed Audit Payload companion records only; it does not silently add them to ordinary results. Show recorded exchange/local-action payloads as bounded historical records with their own line references and available `run_id`/`attempt_id`/`action_id` links. Avoid promising ordinary timeline normalization of nested provider-native inputs. The companion must be a safe regular file and the ordinary Call Log must record enabled audit coverage; lack of a companion or recorded enabled coverage is reported as unavailable, not invented. Coverage validation uses the same scan budget and can fail visibly if it cannot establish availability. Search across many Sessions may return attributed unavailable-source diagnostics and continue; an explicitly selected unavailable audit read/search errors. Mixed enabled/disabled Runs, missing close markers, malformed payloads and partial coverage remain visible; companion existence never proves full Session coverage. Discovery never enables auditing or creates files.

**R15 — Historical data and redaction.** Reading invokes no recorded Tool, shell, Provider, instruction loader, Skill activation, Conversation restore, memory mutation or Resume. Historical instructions stay inside a Tool result labeled as untrusted recorded data; they do not become System Prompt sections or executable arguments. Preserve existing terminal control-character sanitization. Apply `call_log.redact_data`/existing known-secret helpers before match/excerpt/capping and before returning any historical string, including dictionary keys, metadata, diagnostics and errors. Reuse `execute_batch(result_secrets=...)`: current configured provider/Tavily keys and keys protected after in-Run configuration changes remain redacted. Unknown historical secrets are not claimed to be detected. Normal logging of the present discovery Tool invocation remains allowed; historical files are unchanged.

### Question Tool answers

**R16 — Local Other.** For every question with N supplied choices, display the supplied labels numbered 1–N and append `N+1. Other (custom answer)`. Render the full question batch before collecting answers, with existing sanitization and spinner pause/resume. Other is interface-local, not inserted into model arguments and not counted in the model schema's six-choice maximum. Selecting N+1 opens `Custom answer <question number>: ` and returns the entered custom answer, never the Other label. Update the advertised Question Tool description to make this path discoverable.

**R17 — Numeric choice validation.** At a question with choices, trim surrounding whitespace for numeric selection only. A signed or unsigned ASCII integer token (`[+-]?[0-9]+`, including leading zeros) is interpreted as a selection; values 1–N select the supplied label, N+1 opens Other, and every other value displays the valid range and reprompts that same question. Avoid unbounded integer conversion: an enormous token within the answer bound must also reprompt safely. Text not in this integer grammar remains an ordinary direct written answer unchanged. Do not silently store `0`, negative numbers, `10` for four choices, or other invalid integer selections as free text. Decimal-looking prose such as `1.5` remains direct text. The explicit `text: ` prefix takes precedence and returns its nonblank suffix literally.

**R18 — Literal custom/free text and bounds.** Custom prompts treat the whole entered text literally, including `5`, `10`, `text: 5` and whitespace surrounding nonblank text; neither selection nor escape parsing recurs there. Questions without choices retain the existing free-text prompt and `text: ` escape; numeric text is literal. Retain 1–4 questions, 1–500 nonblank question characters, 1–6 model choices of 1–120 nonblank characters (string/text-only object labels), and the existing maximum 1,000 characters per raw answer. Enforce the same nonblank/length rules on each custom prompt, reprompting locally. Do not modify answer result shape: `{answers: [{question, answer}, ...]}`.

**R19 — Existing Question lifecycle.** Invalid selection attempts never reach Tool results/Conversation as answers; a valid answer proceeds in the same routed turn without an extra model retry. Preserve EOF Tool error, KeyboardInterrupt/partial-batch behavior, piped noninteractive handling, logging, provider follow-up correlation and strict Resume of accepted answers. Answering Other or a written `yes` still never confirms another Tool.

### Tests and documentation

**R20 — Isolation and supported surface.** Reuse the suite's temporary-home/cwd isolation, or monkeypatch a narrow internal home lookup before initializing Run storage; remove test-specific destination overrides and legacy flat/path-extension assumptions. Do not add public destination injection merely for testing. Reset captured storage with Call Log's existing test reset. Update concise affected README sections and `.env.example` for the fixed project path, Resume ordering, Tool schema/examples, audit availability, bounds/cursors and Other behavior. Existing unrelated runtime behavior stays covered; no legacy deletion/migration.

## Testing Decisions

- Test behavior through `main()`/`run_repl()`, Call Log's existing path and Resume interfaces, and `Tool Registry.execute_batch` with representative temporary-home files. Pure encoding/path checks can use the retained storage helper; avoid a separate testing architecture.
- Follow existing `test_call_log`, `test_main`, `test_project_instructions_integration`, `test_tools`, `test_detailed_audit`, `test_question_tool` and workspace cap regression patterns. Add a focused `test_session_logs` module for new discovery behavior. Existing fake Providers verify one actual discovery follow-up and accepted Question answers entering the Conversation, rather than invoking a real service.
- Verify sibling projects including flatten collisions, long/Unicode paths, a cwd change after capture, and a recently resumed older Session outranking a newer id. Check `last` excludes current only for Tool aliases, not list/search or startup Resume. Verify explicit cross-project read/search, provenance and project metadata mismatches.
- Compare a timeline fixture containing submissions, follow-up Attempts, intent without execution, actual Tool successes/errors, failed/interrupted turns, clears/undo/compression, and malformed/partial tail evidence against externally expected facts and source lines. Successful and pending snapshots must not duplicate evidence. Strict Resume must reject a malformed log that tolerant discovery can inspect.
- Exercise byte and count bounds with deterministic operation counts, a no-match search page, a line beyond the parse cap, UTF-8 at the output boundary, and continuations until exhaustion. Assert progress and complete unchanged-file coverage, small output, malformed/stale/changed-binding cursor errors, and an explicit selection-budget failure rather than a false last result. No timing-only performance assertions.
- Test symlink directories/files (including replacement between validation/open), FIFO/nonregular files without opening/blocking, forged paths/cursors, missing roots, invalid ids and recorded identities. Assert no effects outside the log root and no activation/execution from malicious historical instructions. Recheck fresh/Resume writes as well as discovery reads.
- Exercise ordinary/audit selection, absent/unrecorded/partial audit coverage, and provider/Tavily secrets in historical values, object keys, headers, diagnostics and errors. Include a key protected before a runtime credential change. Match/excerpt results and logged current Tool output contain no known key.
- Reproduce the four-choice inputs `5` (Other) and `10` (invalid/retry); cover 0/negative/leading-zero/whitespace integer inputs, a six-choice seventh local option, custom `text: 5`, ordinary direct text, no-choice numeric answers, escape, bounds, EOF/interrupt and no accidental Tool Confirmation.
- Validate each ticket's focused regressions and existing affected tests first. Run the complete test suite after all slices integrate. Use the repository's installed pytest through `uv run pytest`; no new test runner/dependency or speculative tests of private algorithms.

## Out of Scope

Legacy flat-log lookup, compatibility, migration or deletion; changing existing Session Ids; arbitrary log destinations or workspace configuration; retention/rotation; semantic search, regex search, embeddings, indexing databases or extra model requests; mutable history, memory curation, automatic Skill activation; extra REPL discovery commands; executing recorded Tools; relaxing strict Resume; snapshot guarantees for concurrent writers; new configuration caps or authentication infrastructure.

## Further Notes

One Session continues across Runs, as ADR-0003/0005/0007 require. Discovery is a tolerant historical reader with bounded evidence output; Resume remains strict state replay. A filesystem scan is deliberately used until an independently scoped feature proves an index necessary. Main owns CONTEXT/PROJECT_STATE updates; implementation owns supported README/env examples, without rewriting old planning artifacts.

Requirement coverage: ticket 01 owns R01–R08 and R20 storage/Resume/isolation; ticket 02 owns R06–R15 and R20 discovery/docs; ticket 03 owns R16–R19 and R20 Question/docs. The overlaps are integration obligations, not duplicate implementations.
