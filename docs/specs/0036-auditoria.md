# 0036 — Auditoria

Brief: `docs/briefs/0036-auditoria.md`. Vocabulary: `docs/CONTEXT.md`. ADR-0003 governs the per-Session Call Log; ADR-0005 governs Resume and the Call Log's replay contract. This feature adds no new ADR: the separate opt-in payload and unchanged replay ownership are settled in the brief.

## Problem Statement

The Call Log can rebuild a Conversation and show Attempts and Tool results, but cannot explain many local REPL decisions or what the Provider actually saw. A resumed Session may span Runs with different audit settings; a trace that silently omits a Run or ends mid-write could mislead its reader.

## Solution

Record compact, safe Audit Events in the existing Call Log in every Run. A per-Run environment opt-in also writes a sensitive, owner-only, per-Session JSONL file containing model-facing exchange details. Explicit Run coverage markers and paired Attempt records expose disabled Runs, failures and incomplete traces. Failed detailed writes stop further actions visibly; only the Call Log rebuilds the Conversation on Resume.

## User Stories

1. As a user, I want the submitted local command and its outcome recorded even when it is invalid, so that I can account for decisions that did not reach a Provider.
2. As a user, I want mode and Tier Pin changes, including Shift+Tab, recorded, so that I can explain later Tool availability and routing.
3. As a user, I want successful and failed Runtime Configuration, Skill and Memory changes recorded without copying hidden keys or Memory Note text into new always-on events, so that I can inspect decisions without exposing those values unnecessarily.
4. As a user, I want Tool Confirmation decisions recorded before execution, so that approval followed by failure is distinguishable from rejection, automatic execution and no confirmation.
5. As a user, I want errors and already recorded Attempts and Tool outcomes to remain visible, so that neither failure nor interrupted work is silently presented as success.
6. As a user, I want to opt into detailed Provider diagnostics separately for each Run, so that I do not pay the sensitivity cost in Runs I did not opt into.
7. As a user, I want an enabled Run's System Prompt, actual sent messages and Tool definitions correlated with its Attempt and answer, so that I can investigate retries, Escalation, Compression and Tool follow-ups.
8. As a user, I want an observable Provider failure or interrupted exchange labeled as such, so that absent answers are not mistaken for successful answers.
9. As a user, I want mixed enabled/disabled Resumes and incomplete Runs to be obvious from their records, so that a partial trace cannot be described as complete.
10. As a user, I want known API keys redacted in new records without obscuring the audit schema or fixed outcomes, and detailed files protected from other local users, so that the new audit feature does not intentionally publish my credentials or misstate actions.
11. As a user, I want sensitive local command bodies available only in the opt-in file when needed, so that the always-on Audit Events do not duplicate `/remember` text or `/config` secrets.
12. As a user, I want `shell` commands, authorization and bounded returned output represented as observed, so that I can inspect what the agent did without false claims about external effects.
13. As a user, I want an auxiliary write failure to stop further work with a visible error while leaving the Call Log and Resume usable, so that missing detailed records are never silently accepted.

## Requirements

- **R1 — Always-on local actions.** Add `audit_event` lines to the Call Log for each submitted slash REPL Command (including unknown, bad arguments and failed commands), with command name, safe arguments or an explicit `arguments_omitted` marker, and `ok`/`error`/`cancelled` outcome as appropriate. Record effective state transitions for `/mode`, `/model`, `/config`, `/skill`, `/remember`, `/forget` and interactive Shift+Tab with old/new non-secret state where useful. `/remember` never places its text in a new always-on event; `/config` never places typed keys, secret prompts, or saved credential values there (use provider/tier/setting names and success/failure only); `/forget` uses index, not removed text. Invalid submissions and unsuccessful or cancelled mutations do not claim a state change. Keep existing Call Log `turn_end`, clear, undo, compression, Attempt and Tool entries and their Resume effects; new entries are ignored by the replay reader. Existing full Conversation/Tool records remain governed by ADR-0005, not replaced by sanitized summaries.
- **R2 — Tool decisions and outcomes.** For each Tool that actually requests Tool Confirmation, write an `audit_event` with Tool call id/name and `approved` or `rejected` before any apply; include Strong Confirmation rule names when present, without copying the preview, raw typed answer or secret-bearing argument. Existing `tool_execution` records carry validated arguments, bounded result/error and `dangerous_rules`; retain their normal order and semantics. `auto` without a prompt does not claim human approval. Rejections, validation failures, failed applies, non-zero shell exits, Tool batch correlation errors and interruptions remain distinguishable through Tool result, Turn End and/or an Audit Event where the existing record does not represent the outcome. For `shell`, its existing command argument and returned capped stdout/stderr/exit_code (or error), including `[...truncated]` marker as actually produced, are evidence of what the agent observed, not evidence of all external side effects.
- **R3 — Per-Run coverage and location.** `PA_DETAILED_AUDIT=1` enables detailed auditing for a Run; unset or `0` disables it; other values fail configuration before a Run starts. Resolve a companion file by replacing the Call Log file's final extension with `.audit.jsonl` (or appending `.audit.jsonl` to an extensionless Call Log); honor `PA_LOG_PATH`, reuse the Session Id and directory, never create a second Conversation file. Each Run has an opaque `run_id` in its Call Log `audit_coverage_start` and `audit_coverage_end` (`enabled: true/false`) regardless of setting, and the enabled file has paired `run_start` and `run_end` with the same id. Disabled Runs do not append detailed records. Start coverage before REPL actions, close only on ordinary Run exit; missing end or a dangling begin means incomplete coverage, not a successful finish. A resumed Run reads only the main Call Log for Conversation; no migration of old logs and no requirement to read auxiliary files when detail is off.
- **R4 — Detailed Provider exchanges.** For every Attempt when enabled, including each retry, Escalation, Tool follow-up and Compression Attempt, write `attempt_start` before calling the Provider with the actual System Prompt, ordered normalized messages, full advertised Tool definitions or explicit empty Tool set, tier/provider/model and unique `attempt_id`. Include the Provider-owned replay input when used for a Tool follow-up, to the extent it is model-facing, not vendor HTTP bodies. Add `attempt_id` to that Call Log Attempt without changing its existing fields; emit matching `attempt_end` with normalized answer and Tool calls plus outcome `ok` or `error` when observable. Include a redacted error for caught Provider failures; an interrupted process may leave only `attempt_start`. Treat the answer as the normalized result visible to the Router, not an unparsed vendor response. No new Provider calls, HTTP headers, credential-bearing auth metadata or raw requests/responses.
- **R5 — Sensitive material.** Reuse known-key literal replacement (current and earlier Runtime Configuration keys from the Run, and the known Tavily key) for user-controlled and external data in new Audit Events and detailed records, including nested Tool arguments, System Prompt, messages, replay data, answer and errors. Preserve schema-owned field names at every level and fixed controlled event/outcome/state values (for example `outcome: ok` and `mode: auto`) even if a credential equals one of those literals. This distinction is based on the origin of a field, not the spelling of its value: a user-supplied string equal to `ok` is still data to redact. Dynamic dictionary keys supplied by a model/user or an external source, including keys inside Tool arguments and detailed payloads, are data too: redact credentials within those keys as well as their values while leaving enclosing schema fields and controlled values intact. Never put an intentionally collected `/config` secret into audit records even with opt-in. Optionally store submitted `/remember` text only in an enabled file as a local-command detail linked by `run_id`; otherwise record only metadata. Unknown private text may appear in the opt-in file; the program does not promise to detect all secrets. Create the companion with owner-only permissions (0600), keep it owner-only when appending and do not follow an unexpected symlink; default directory is `~/.personal_agent/logs/` (outside the repo), and a user-provided `PA_LOG_PATH` inside Git is their responsibility. Document access, format and sensitivity without adding a reader.
- **R6 — Fail closed, without corrupting Resume.** When detail is enabled, failure to open/protect/write/flush the auxiliary file, including `run_start`, `attempt_start`, outcome, command detail or `run_end`, raises an audit-specific fatal error visible to the user and prevents subsequent REPL commands, Provider retries, Tool calls and local mutations. Write a compact auxiliary `action_start` before each submitted REPL Command or requested Tool (including invalid, auto-approved and read-only calls), with a unique `action_id`, safe identifiers and no additional raw secret input; put the same id on its subsequent main Call Log Audit Event or `tool_execution` to link its observed outcome. Write `attempt_start` before each Provider call. A start without an outcome is an incomplete action, not proof it succeeded; if writing an outcome fails, do not take another action. Never convert this error into an ordinary retryable Provider failure, Tool result or successful Turn End. Keep the main Call Log readable/replayable; a missing companion end, unmatched start or partial final line explicitly means incomplete coverage. On an enabled Resume, refuse to append to an existing malformed partial JSONL tail with an actionable error (do not silently discard data); disabled Resume can still use the Call Log. A process crash, write failure after an effect, or lost bytes may prevent recording its outcome; never fabricate an outcome or claim crash-proof durability.
- **R7 — Compatibility and observability.** Call Log remains the only source for Resume; opt-in file is never consulted for tier routing, budget, Conversation or Todo List. New entries do not change `log_version: 2` replay behavior or existing Session Id discovery. The flag and write error are described in user documentation; audit records carry timestamps, Session Id and Run/Attempt links sufficient to distinguish events across Resumes, with JSONL parsable per complete line. No automatic retention or pruning; keep the companion under the same operator-controlled retention policy as its Call Log.

## Implementation Decisions

- Extend the Call Log with explicit `audit_event` and `audit_coverage_*` writers, using an opaque `run_id` per Run. Keep the legacy Attempt fields and add one `attempt_id` only for detailed correlation (not derived from millisecond timestamps, which can collide); old Attempts without it remain valid. A coverage start/end is written in the Call Log even when disabled, and enabled file markers share the id. The main reader's existing type filter ignores all new entries.
- Add a small companion writer beside the Call Log rather than a second replay mechanism. Open newly created files with 0600 permissions; refuse an existing symlink or file accessible to group/others rather than silently changing its permissions. Append complete JSONL records; check the tail before appending to avoid hiding a previous partial line. Failure propagates as a fatal audit error to the REPL boundary, not through ordinary Router/Tool retry paths. Even if a failure leaves an unterminated last line, Call Log Resume must stay independent of that file.
- Instrument the REPL at command dispatch and mode-toggle boundary for local outcomes, and the Tool Registry at confirmation for actual user decisions. Log before a state-changing command or Tool apply where the detailed writer is enabled; log resulting state/outcome after it, acknowledging that an interrupted or failed result write may leave a pending intent. Keep command-body exclusions explicit rather than sanitizing a stored raw command after the fact.
- Instrument the Router's common Provider exchange path, including Compression, at the point the System Prompt and arguments are fixed for a single Attempt. Capture the same advertised Tool definitions and normalized messages passed to `Provider.call`, plus the provider replay input used there. Never treat a failed audit write as a Provider exception to retry. Existing redaction helpers cover known keys before either new writer sees a value; do not alter existing Conversation replay payloads just to make a new Audit Event smaller.
- Keep the Router's existing Call Log Tool-argument redaction consistent with the same distinction: schema fields remain legible, but dynamic argument keys containing a known credential are redacted. Existing `shell` Tool Output Cap and actual Tool result are authoritative; do not capture arbitrary extra process output. These choices refine the brief without superseding ADR-0003/0005.

## Testing Decisions

- Test user-visible behavior and on-disk JSONL through scripted `run_repl` and fake Provider transport (`tests/test_repl.py`, `tests/test_call_log.py`, `tests/fakes.py`) as the highest practical seam; use existing `tests/test_routing.py`, `tests/test_agent_mode.py`, `tests/test_input_box.py` and `tests/test_shell_tool.py` for focused failures. Assert records and actual side effects, not just calls to a logging helper. Stub external transport and file-write failures; do not use paid Providers or dangerous shell commands.
- With detail disabled, assert no companion file, compact command/state/confirmation outcomes including invalid/failed paths and Shift+Tab, no leaked `/config` key or `/remember` text in new Audit Events, unchanged replay of clear/undo/compression and existing Tool/Attempt line meanings. Use known keys equal to schema field names and fixed values such as `ok`/`auto` to verify those fields/values remain legible, while user-controlled strings with those spellings are redacted.
- With detail enabled, compare recorded System Prompt/messages/Tool definitions (including Skill, Memory, Todo and Compression differences) and follow-up replay to the fake Provider's actual inputs. Assert distinct linked Attempts for retries, Escalation and Tool rounds; both success and caught Provider failure; no HTTP headers/raw vendor bodies. Assert known-key redaction recursively, including keys entered then replaced within one Run and credentials embedded in dynamic Tool-argument/detailed-payload dictionary keys; verify the same for the existing Call Log Tool arguments while schema field names and controlled values remain unchanged. Do not pretend arbitrary private text is detected.
- Exercise fresh→Resume enabled/disabled permutations, complete and interrupted Runs, partial auxiliary tails, startup/attempt/outcome/command/end write failures, and verify no further Provider/Tool/local action after a failure while `load_conversation` can still replay a valid Call Log. Check owner-only file modes with restrictive/open existing files; check Tool confirmation approval vs rejection and failed apply, `auto`, bounded `shell` stdout/stderr/nonzero/timeout/rejection. Run the offline test suite.

## Out of Scope

Deterministic re-execution, external state snapshots, unbounded shell stdout, keystrokes, spinner/terminal redraws, arbitrary raw Tool output, cryptographic integrity, tamper-proof storage, an audit-viewing REPL command, automatic pruning and new Provider billing calls.

## Further Notes

An enabled Run with an absent/malformed auxiliary file cannot be called fully traced even if its main Call Log remains valid. Existing Call Logs created before this feature have no coverage claim; absence of coverage markers on them means unknown, not disabled or enabled.
