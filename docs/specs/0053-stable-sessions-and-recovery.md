# 0053: Stable sessions and file recovery

## Problem Statement

A Session can change model at submissions 5 and 15 even when the user wants a stable route. OpenRouter receives no durable affinity identifier, and variable Memory and Todo content precede reusable instructions. The existing Session Report cannot clearly relate task/model changes to cache observations, and direct-provider estimates lose cache information. Approved file mutations cannot be recovered with `/undo`, which changes only Conversation. Prompt and Tool changes have behavioral tests but no complete reviewed surface fixture.

The evidence is recorded in the [approved brief](../briefs/0053-stable-sessions-and-recovery.md), [routing research](../research/done/2026-10-14-cache-and-session-routing.md) and [reference research](../research/done/2026-10-14-reference-opportunities.md). These establish local behavior, not measured savings or model-quality improvement.

## Solution

Evaluate automatically once before the first routed task, then retain the selected tier until an explicit selection or evaluation request. Carry the existing Session Id into OpenRouter requests, order stable prompt content first, and show bounded recorded task/model/cache evidence through `/report`. Add `/recover` to preview and explicitly confirm restoration of the latest routed execution that changed files through `write`, `edit` or `apply_patch`. Preserve Conversation Undo. Review deterministic production prompt and Tool-schema fixtures for every Agent Mode.

## User Stories

1. As a user, I want initial automatic selection, so that I can begin without choosing a tier.
2. As a user, I want my selected tier to remain stable beyond tasks 5 and 15, so that later simple tasks do not trigger maintenance calls.
3. As a user, I want to select a tier before my first task, so that no evaluator call is necessary.
4. As a user, I want `/model auto` to request one evaluation while retaining my selected tier, so that I control when routing changes.
5. As a user, I want only manual selection to lower my tier, so that explicit evaluation cannot undo my chosen baseline.
6. As a returning user, I want old logs and pending work to Resume, so that a policy change does not discard my history.
7. As a user, I want failed and interrupted requests retained in evaluator input, so that an explicit evaluation sees accepted work.
8. As an OpenRouter user, I want the same affinity identity through turns, retries, Tool follow-ups and Resume, so that the Provider can associate my ordinary requests.
9. As a user, I want auxiliary calls separated from ordinary affinity, so that their different prompts do not compete for the ordinary association.
10. As a user, I want stable rules before changing context, so that matching prefixes can be reused where supported.
11. As a user, I want Memory, modes, Skills, Todo, Compression and current Project Instructions to remain effective, so that caching changes do not freeze my instructions.
12. As a user, I want `/report` to show task outcomes and routes alongside cache evidence, so that I can inspect changes without another model call.
13. As a user, I want missing measurements distinguished from zero, so that partial evidence does not become a claim of no caching.
14. As a direct-provider user, I want cache reads and writes included in local cost estimates, so that estimates account for the measured work.
15. As a user, I want to preview file recovery separately from `/undo`, so that I know which workspace effects will change.
16. As a user, I want file creation, modification and deletion recoverable after Resume, so that restart does not lose my checkpoint.
17. As a user, I want successful file mutations from a failed or interrupted execution recoverable, so that a failed answer does not strand its edits.
18. As a user, I want external edits and unsafe paths to block restoration, so that recovery does not overwrite later work.
19. As a user, I want Retry after recovery to start from my request, so that obsolete Tool results cannot be treated as still applied.
20. As a user, I want explicit bounds and exclusions for checkpoint storage, so that recovery is predictable and protects excluded files.
21. As a maintainer, I want deterministic reviewed fixtures of production prompts and schemas, so that unintended model-facing changes are visible offline.
22. As a maintainer, I want meaningful existing regression tests preserved, so that a fixture does not replace execution-gate, persistence or replay checks.

## Requirements

### Stable selection

- **R1 — Initial selection:** A fresh Session starts pending and evaluates once before its first routed execution, unless manual `/model <tier>` selected a tier first. After completed initial selection/fallback there are no scheduled evaluations, including submissions 5, 15 and beyond, on either fresh or resumed Sessions. Resume itself makes no evaluator call.
- **R2 — Explicit control:** `/model <easy|medium|complex>` immediately selects, may lower the tier and cancels an outstanding request. `/model auto` retains tier, accepted-submission count and evaluator input, and requests one evaluation on the next routed execution, including Retry. Repeating it before execution coalesces into one request; it enables no schedule. Explicit evaluation keeps or raises a selected tier; only manual selection lowers it. `auto` Agent Mode remains unrelated.
- **R3 — Identity and input:** Keep exact accepted submission text/count, original Retry ordinal, cumulative input since Clear and attribution independently of Conversation. Failed/interrupted/manual-period submissions participate once; retries, Tool follow-ups, Question answers and local commands add no submission. Clear removes input and pending continuation, retaining tier/count/request; Undo and Compression retain evaluator input. Historical lines are never rewritten or deleted.
- **R4 — Failure and cancellation:** Retain full bounded easy-route evaluation, exact tier-label validation, retry allowance, accounting and purpose separation. Completed evaluator failure visibly chooses initial medium or keeps an existing tier, consumes its request and permits ordinary dispatch. Cancellation stops ordinary dispatch and preserves outstanding initial/explicit evaluation across Resume. An obsolete scheduled checkpoint on a selected historical Session alone must not become an outstanding request.
- **R5 — Historical replay and migration:** Strictly replay valid policy-version-1 records using the historical 1/5/15 rules before converting runtime state. Preserve tier/count/input, completed Conversation, Summary, Todo and pending continuation. Convert to policy version 2 durably before accepting commands/submissions or dispatch; retain genuine pending initial or explicit evaluation, drop every scheduled checkpoint. Policy-less selected logs retain selection with no evaluation; pending logs retain their one-off; missing tier keeps the existing once-warned medium fallback. Initialize absent tracking empty without inferred old submissions. Malformed present state still fails Resume.
- **R6 — Persistence and routing:** Writes of submission, migration, commands, Clear and completed evaluation precede corresponding live changes and dependent dispatch, using append-prefix restoration on observable failure. Persistence/detail failure is fatal, never evaluator fallback. Keep same-route transient retries, context recovery, configuration snapshot, provider-neutral budgets, spend provenance and ordinary `/usage` separation. Runtime Configuration changes remain explicit user actions and do not trigger evaluation.
- **R7 — Presentation:** Interactive footer, piped notices, `/model`, help and current behavior documentation describe initial or explicitly requested evaluation and retained tier. Remove claims that auto enables remaining checkpoints or that tasks 5/15 evaluate. Present pending evaluation separately from the selected tier.

### Session cache affinity

- **R8 — Ordinary identity:** OpenRouter receives top-level `session_id` equal to the durable Session Id on every ordinary exchange, both streaming and nonstreaming: first dispatch, Tool follow-ups, transient/context retries, explicit Retry, subsequent turns and Resume. Separate Sessions differ. Do not expose credentials, machine paths or accepted task text in the identifier.
- **R9 — Auxiliary identity and compatibility:** Evaluator and all manual/preventive/overflow Compression calls use deterministic distinct keys `<Session Id>:tier_selection` and `<Session Id>:compression`, stable through auxiliary retries and Resume. Forward optional request identity through the existing exchange/Provider seam; other Providers accept or ignore it without sending OpenRouter fields. Direct standalone Provider calls without Session identity omit the field. Preserve `sort: price`, preferred minimum throughput 85, parameter requirements and current diagnostics behavior.
- **R10 — Honest guarantee:** Affinity is best effort and per model; document no guaranteed hit, cache survival after idle time, shared processing across models, or route immutability after explicit configuration/selection. Add no metadata poll, prewarm, cache-control activation or dependency.

### Prompt surface and fixtures

- **R11 — Prompt order:** Ordinary prompts begin with application identity, fixed Tool/trust rules, current Agent Mode rules and language behavior, followed by the task's Project Instructions snapshot. Place variable Memory, active Skills, Conversation Summary and Todo after this stable prefix, in that deterministic order. Changing only a Todo, Memory note, Skill or Summary preserves all preceding stable bytes. Keep each instruction's priority and execution gates explicit; do not silently drop content to improve reuse.
- **R12 — Live behavior:** `/remember` and `/forget` affect the next ordinary request; active Skill order/snapshots retain their current semantics; unfinished Todos update through Tool follow-ups and completed ones disappear; manual/preventive Compression preserves replay and Todo. Project Instructions reload on each task/Retry and stay fixed within it. Live mode changes affect subsequent exchanges and execution boundaries immediately, including while confirmation is pending. Mode/Tool/project changes legitimately change the prefix. Keep current_time out of the prefix and all Provider translations/budget counting faithful to the prepared input.
- **R13 — Deterministic Tools:** Preserve production Tool availability per mode and configuration, with one deterministic order for identical effective catalogues and deterministic effective Skill descriptions. Provider translations preserve that order, schemas and replay. Do not sort JSON arrays whose order is meaningful or silently replace production definitions with fixtures.
- **R14 — No cache claim from string tests:** Prove a longer stable common prefix under a variable-context change using production prepared inputs for all four Providers; preserve complete prepared input and budgets. This is a structural test, not a promise of cache hits, lower latency, savings or full-history reuse after a system change.
- **R29 — Production snapshots:** Commit one readable deterministic fixture per `plan`, `build`, `auto`, rendered through production prompt construction and effective Tool definitions using an isolated fake Provider/transport, temporary workspace and synthetic Project Instructions, Memory, Skill, Summary and Todo. Include the complete system text and ordered canonical Tool schemas; capture the request seen by the fake Provider rather than a copied prompt implementation.
- **R30 — Isolation and sensitivity:** Fix configuration, optional Tool gates and synthetic Skill catalogue; use synthetic model names and empty/synthetic credentials. Prevent network, credential discovery, real home/config/context and machine-specific paths. Temporary directory, clock, environment credentials and hash randomization must not change fixtures. Do not mask changes to prompt text or schema; normalize only nondeterministic fixture setup values that are explicitly fixed.
- **R31 — Review and tests:** A real prompt or schema change fails comparison until the reviewed fixture is deliberately updated. Provide a small documented developer regeneration path under tests, with offline operation and inspectable fixture diffs. Keep behavioral permission, Memory, Skills, Todo, project reload, budget, Compression and Provider replay tests. Add no runtime REPL command or model-family fixture variants.

### Recorded task/model/cache evidence

- **R15 — Sequence:** Extend local `/report` with chronological rows for the latest 20 opened routed executions, labeled original ordinal, submission versus explicit Retry, Run/execution boundary, recorded Turn End outcome (or unresolved), tier and actual Provider/model route(s). Bound retained per-execution route groups to 16, with omission notices. Relate Attempts to explicit openings/closures rather than matching text or inferring submissions from Attempts. Older/unattributed records remain in existing aggregates with unknown attribution.
- **R16 — Measurements and comparisons:** Each ordinary task/route row shows Attempt/retry counts, Provider duration, first-text measurements/coverage, prompt/output/cache-read/cache-write totals and reported versus estimated cost. Mark observed Provider/model changes from the preceding known ordinary route and show cache observations on both sides through adjacent rows. Keep evaluation/Compression separately labeled, including those executed inside a task. Optional recorded upstream diagnostics may be shown when safely correlated; their absence is unknown. Report observations, never causal savings or cache invalidation inferred from a model change.
- **R17 — Coverage and bounds:** Absent, invalid, partial and unknown counters remain distinct from known zero, including failed Attempts and streamed partial usage. A cache-read fraction is `sum(cached_tokens) / sum(prompt_tokens)` only over the same compatible known samples with positive denominator and valid counters; display its sample coverage. Exclude inconsistent subsets, not valid independent metrics. Bound total rendering to 16 KiB, row/group state and diagnostic lists; preserve Session aggregates and their coverage before optional detail. Scan with existing bounded record reader and visibly report truncated/partial inspection. Keep existing secret redaction and terminal sanitization.
- **R18 — Normalized cache counters:** Preserve cache-read/write counters for streaming, nonstreaming and available failure usage for all four Providers. OpenRouter/OpenAI use `prompt_tokens_details.cached_tokens/cache_write_tokens`; Anthropic uses `cache_read_input_tokens/cache_creation_input_tokens` with total prompt equal to noncache input plus cache reads plus cache writes; Gemini uses `cachedContentTokenCount` as a subset of `promptTokenCount`. Do not double-add subsets. Only present valid nonnegative integer counters are known; booleans, negatives and malformed details are invalid, never coerced to zero. Retain available independent counters on malformed/partial evidence under existing stream-error semantics.
- **R19 — Cache-aware estimates:** OpenRouter's reported cost stays authoritative and is never recomputed. Direct-provider Estimated Cost uses the locked local LiteLLM cost calculator with complete normalized usage/cache breakdown, including reported cache-write TTL breakdown where applicable; do not hardcode today's price multipliers. Verify actual locked-library semantics for each Provider so cache tokens are billed once at applicable rates. Unsupported pricing, invalid required counts or an incomplete breakdown that cannot support a correct estimate produces unavailable cost, never a fabricated zero. Missing cache counts may be treated as zero for calculation only where the Provider contract establishes omitted-zero semantics; report coverage still retains absence. All estimates remain flagged estimated and Run spend charges available cost once.
- **R20 — Local-only behavior:** `/report` reads recorded evidence across Runs, accepts no new arguments and makes no Provider/model/metadata calls, tokenizer downloads or configuration changes. It preserves Conversation, tier/input/progress, pending work, latest `/usage` and Run spend, apart from its existing local Audit Event. Old logs need no retrospective normalization or rewrite.

### File checkpoints and recovery

- **R21 — Unit and eligibility:** The latest routed execution with at least one actual successful file mutation is recoverable even if it ends error/interrupted or has no Turn End after process death. An execution is one explicit submission or Retry opening, identified by existing Session/Run identity and opening-record position plus original ordinal; Retry keeps that ordinal but gets its own checkpoint. Earlier Retry executions' mutations are outside that set. Capture only `write`, `edit`, `apply_patch`; never shell effects or all workspace files. No-op/rejected/failed-and-fully-rolled-back operations do not replace the previous recoverable execution. Within one execution, coalesce each canonical file to its first before-state and final after-state, checking continuity at every repeated mutation.
- **R22 — Exact states and safe storage:** Before/after include absence versus regular file, exact bytes, permission mode and validated in-root path/link identity; hashes aid integrity checking but never replace restorable bytes. Do not redact snapshot bytes. Store in a versioned owner-only checkpoint companion below the existing project-scoped Session storage, separate from Call Log/audit/Git. Never embed snapshot payloads in model messages, discovery output, reports or audit records. Inherit `.env`, `*.pem`, `*.key` exclusions on supplied/resolved paths; exclude recovery storage itself if home/storage is within Workspace Root. Reject links/nonregular storage and malformed/wrong-project/session manifests. See the persistence contract below.
- **R23 — Capture before mutation:** At the approved apply boundary, revalidate path, prepared before-state, exclusions, file/total/path bounds and live mode after confirmation, then persist a recoverable operation intent before disk mutation. Persist observed after-state before declaring mutation safely checkpointed or permitting another dependent Tool/Provider exchange. Capture cannot occur only after Tool returns, or a cancellation could lose a successful write. A capture failure before mutation leaves files unchanged; an after-state/promotion failure stops the Run, retaining the journal and reporting uncertainty. Preserve apply_patch's own rollback; strengthen single-file write rollback where a failed write can leave partial bytes. Do not describe an incomplete/corrupt checkpoint as available.
- **R24 — Preview and confirmation:** `/recover` with no arguments is a local-only command showing the latest eligible execution, routed outcome/uncertainty, paths, create/modify/delete reversal and a bounded sanitized diff from current after-state to before-state. It names the exact execution/ordinal, exclusions, storage limits, shell exclusion and the fact that older Retry executions are outside the set. Require full literal `yes` to restore, in interactive and piped input, even in auto; other input/EOF/Ctrl+C cancels unchanged. In plan mode show preview but reject mutation with `/mode build|auto` guidance. Add help/completion. Preview includes no Provider call and does not change Conversation or consume the checkpoint.
- **R25 — Conflict and path refusal:** Validate every current path against recorded after-state before confirmation and again after confirmation/before restore. Any content, existence, permission, link-topology, parent-boundary, project or integrity mismatch refuses the whole recovery, naming conflicts without overwriting any file. Preserve supported in-root leaf symlinks when their topology/target remain unchanged; do not follow outside-root or replaced links. Reject hard-linked mutation targets rather than promising confinement over untracked aliases. Untouched files remain unchanged; do not recreate missing parents or delete directories. Concurrent Session Runs remain unsupported; this does not promise protection against an actively racing external writer.
- **R26 — Restore and failure:** Restore creation by removing the created regular file, deletion by recreating the original file, and modification by restoring exact original bytes/mode while preserving validated leaf links. Prevalidate the full set, persist restoration intent, then apply locally. If an operation fails, roll restored files back to their known after-states where possible; display failures and affected paths and retain recovery metadata. Failed rollback/persistence stops the Run and blocks further mutations/dispatch until the unresolved journal is reconciled or visibly refused. A successful restore consumes this checkpoint; repeating `/recover` reports already recovered/no available checkpoint and never silently steps back to an older execution. Record compact recovery start/completion/failure in Call Log; old history stays intact.
- **R27 — Resume and continuation safety:** On Resume reconcile operation/recovery journal states without automatically restoring files or executing Tools. An interrupted pending mutation whose current file equals exact before-state contributes no mutation; exact intended after-state can be accepted as observed; any third state is unresolved and refuses unsafe recovery/dispatch. An interrupted restore can be reconciled only against recorded before/after states and cannot appear completed while some paths remain unrestored. Before the first recovery write, durably invalidate continuation for the target execution. If it is the current failed task, retain its request/ordinal as fresh Retry data, clear all old assistant/Tool results, fetched URLs and Gemini replay, and rebuild Todo from completed Conversation. Subsequent `/retry`, including after Resume, starts from the user text with current route/config/mode rather than assuming undone Tools succeeded. Preserve an unrelated later pending execution; recovery does not remove successful Conversation turns, Summary or evaluator input, and a successful task's existing `/retry` Undo behavior remains unchanged. If recovery later fails or is interrupted after its intent, the conservative continuation invalidation remains in force.
- **R28 — Retention, limits and legacy:** Retain only the latest changed execution plus staging/incomplete restoration data needed for safety; later read-only tasks, `/clear`, `/undo` and Compression do not erase the checkpoint. Replace older checkpoint only once a newer execution has an actual durable mutation; after recovery do not expose older ones. Bound a file image by the lesser of current `PA_MAX_WRITE_BYTES` and 4 MiB, 64 canonical paths per execution, and 16 MiB of combined before/after/intended snapshot bytes. Each encoded manifest is at most 24 MiB; the saved/staging/temp set is at most 80 MiB per Session. Reject a would-exceed Tool operation before mutation with a clear bound error; no silent truncation/eviction within a recoverable set and no new configuration variables. Legacy Sessions with no companion Resume normally and report no historical checkpoint. Never synthesize originals from Tool arguments, redacted log results or Git.

## Implementation Decisions

### Existing ownership and seams

Retain the REPL as Session owner, `routing/session` as pure policy transitions and Call Log as durable routing/Conversation record. The Router still executes an explicitly supplied tier. Reuse the exchange's purpose and current Session identity rather than introducing another Session identifier or request-context framework. Add only an optional identity keyword at the existing Provider call seam; update the four built-ins and test fakes together. This field affects OpenRouter HTTP metadata, not prepared prompt/token counting.

Reorder the production prompt builder; retain the Registry's single effective catalogue and Provider preparation. No frozen prompt cache or new injection/history format is necessary. Reuse Session Report's record scanner, coverage accounting and redaction, expanding bounded chronological details rather than adding a dashboard or report subsystem.

One small file-checkpoint module earns its existence by sharing bounded storage, exact state validation, mutation journaling and restoration between the three file Tools and `/recover`. Its callers supply execution identity and prepared file effects; it owns snapshot format and integrity/rollback details. Integrate at existing two-phase prepare/apply boundaries and REPL execution openings/closures, never generic wrappers around every Tool. Compare alternatives: post-return capture misses successful writes before interruption; Call Log content is redacted and not an exact before-image; Git changes the user's repository and cannot recover nonrepositories. A separate exact companion avoids these defects while keeping Conversation solely in Call Log.

### Routing policy version 2

Keep outer Call Log `log_version: 2`, submission records and existing tier/source fields. Newly written `routing_policy` has exactly `version: 2`, `mode` (`automatic`, `manual`, `legacy`) and Boolean `evaluation_requested`; there is no `next_checkpoint`. Fresh automatic pending state requests initial evaluation. Selected automatic/legacy state evaluates only when requested; manual requires a selected tier and no request. Completion clears request, preserving mode. Manual selection clears it, auto sets it.

Replay version 1 using its original schema and transition semantics from spec 0041, including old start state and pending checkpoints. Append one `session_routing_policy_migrated` record carrying existing tier and full version-2 policy before live conversion/acceptance on first Run under this feature. Validate it against precisely the replayed state: same tier/count/corpus; requested if old `evaluation_requested` or pending tier, not because selected state has a scheduled due checkpoint. Its implicit preserved count/corpus avoids duplicating cumulative input. Policy-less logs initialize tracking using the existing `source: legacy` boundary with version-2 policy. Mixed logs may transition once from old to new; reject backward/unknown policy versions and malformed or inconsistent migrations. No log rewriting or retrospective paid evaluation.

### File checkpoint persistence contract

Use a fixed directory `recovery-<Session Id>/` under the existing project storage. Open it and fixed manifest names with the same descriptor-relative no-follow/regular-file discipline as Session storage. Directory mode 0700, file/temp mode 0600; reject unexpected owner or unsafe existing permissions rather than copying payloads to a permissive location. Bound reads before parsing and validate schema, base64, path counts, byte counts and hashes. The companion is local recovery state, not evidence of tamper resistance or a general backup.

A manifest contains integer format version 1, project/root/Session identity, original ordinal, Run Id and Call Log opening position, closed outcome or unresolved marker, state (`capturing`, `ready`, `restoring`, `recovered`, `unresolved`), and ordered file entries. A file entry names supplied path and canonical relative target, preserved leaf-link identity when applicable, first before-state and latest committed after-state. A state is absence or exact base64 bytes plus regular-file permission mode and integrity hash. A pending operation additionally records the immediate expected before-state and intended after-state for all paths in one Tool call; restoration intent similarly records progress. Metadata must not require another UUID scheme or snapshot the full prompt/task/history.

Write complete bounded manifests by owner-only temporary write, flush/fsync and atomic replace (and directory fsync where supported). Keep at most latest and active manifests plus one bounded temporary file; finish/promote safely before pruning the older checkpoint. Snapshot/journal durable ordering must cover interruption before/after each file and before final manifest promotion; use recorded before/intended-after for safe reconciliation, refusing ambiguous partial changes. Do not promise atomic multi-file filesystem changes or repair after unobservable filesystem corruption.

Add compact `file_recovery_started` / `file_recovery_finished` records with execution reference, ordinal and outcome, no bytes. Start is append-restored/fatal and precedes restoration; pending loader replay uses the matching execution reference to clear obsolete continuation and retain only fresh Retry request/ordinal. Recovery manifest plus recorded intent must remain consistent after process death; no action resumes Tools automatically. The successful completion record is written before declaring success/consuming live availability. Observable completion-write failure rolls files back where safe or leaves an explicit unresolved journal and halts; never reports success with unrecorded invalidation.

### Local report correlation and accounting

An execution's identity is its explicit Call Log opening position and Run, with ordinal a display/submission identity. Attribute physical Attempts between opening and Turn End/next opening/Run boundary; a maintenance purpose does not open an execution. Manual Compression outside an execution remains unattributed maintenance. An old Attempt without enough boundary evidence is unknown, even when its task string matches a known submission.

Use local LiteLLM 1.102.0 from `uv.lock`; its installed `cost_per_token` has cache-read/write arguments and a usage-object path. Verify Provider-specific inclusion/exclusion against that installed source, not only newer Context7 examples. Keep monetary subtotals and fractions based on compatible samples; a corrected estimate is still not a billed amount.

## Out of Scope

Automatic periodic/continuous evaluation or downgrades, cost-based route changes, cache warming/native Claude activation, external benchmarks or quality claims, paid API calls, new dependencies/SDK migrations, model-family snapshots, new runtime snapshot command, shell undo, full workspace/history backup, directory restoration, arbitrary checkpoint selection, redo or nested undo stack, Git manipulation, `/fork`, new MCP integration, background jobs, dashboards, concurrent Session Runs and generic architecture refactors.

## Further Notes

This spec supersedes spec 0041's runtime schedule and `/model auto` behavior while retaining its historical replay contract. [ADR-0009](../adrs/0009-stable-session-selection.md) records the policy amendment; [ADR-0010](../adrs/0010-file-checkpoints-and-recovery.md) records exact file companions and continuation invalidation. These decisions are approved for implementation, not a claim that feature 0053 is already shipped.

Official behavior was checked on 2026-10-14 through Context7 (OpenRouter `/openrouterteam/docs`, LiteLLM `/berriai/litellm`) and current primary documentation: [OpenRouter affinity/cache](https://openrouter.ai/docs/guides/best-practices/prompt-caching), [Anthropic token accounting](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [OpenAI caching](https://developers.openai.com/api/docs/guides/prompt-caching), [Gemini caching](https://ai.google.dev/gemini-api/docs/caching), and the locked local LiteLLM source. OpenRouter accepts a top-level affinity key of at most 256 characters; the existing Session Id and purpose suffixes fit that bound. Anthropic's three input categories are disjoint; normalized total counts all three. No fixed pricing values are adopted.

All six priorities map to five vertical tickets. Prompt ordering and snapshots share one complete surface-change ticket; each other behavior is independently useful. There are no necessary blocking edges: sequential execution/review is an orchestration constraint, not an invented dependency. Recovery must have an isolated implementation and review; batching it with another ticket is prohibited.
