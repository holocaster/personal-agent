# 0057: ChatGPT subscription Provider

## Problem Statement

Personal Agent currently requires an API key and a Models.dev-admitted Provider/model before opening the REPL. Users cannot authorize their own ChatGPT plan, discover that account's models, or distinguish plan consumption from accumulated API spend. Substituting an OAuth token for an OpenAI API key would also use the wrong request, authentication and replay contracts.

The [consolidated brief](../briefs/0057-chatgpt-subscription-provider.md) is authoritative. The [research](../research/2026-10-20-chatgpt-subscription-provider.md) supplies observed protocol fixtures, not permission to depend on deviations from official documentation.

## Solution

Add the distinct `chatgpt` Provider. Users enter the REPL, run `/connect chatgpt`, authorize in their local browser and explicitly choose an account model. The existing `/model`, `/models` and `/config` flows work with either ChatGPT or existing API-key Providers. A connection alone never changes the route. The route's access method, context occupancy and usage reporting describe the selected route accurately. All existing task, Tool, Session and Subagent behavior remains available with account-safe continuity.

## User Stories

1. As a new user, I want to open the REPL before configuring a route, so I can connect or configure credentials there.
2. As a ChatGPT subscriber, I want to authorize my own account in my browser, so the application can use my eligible plan without an API key.
3. As a returning user, I want valid credentials reused and renewable credentials refreshed, so routine launches do not reopen login.
4. As a user, I want a clear first-login explanation of plan use and a Manage usage destination, so I understand the account I am authorizing.
5. As a user, I want account model display names and exact slugs in an arrow-key picker, so I can select an available model deliberately.
6. As a user, I want cancelled login, cancelled selection and failed saves to preserve my earlier route, so configuration does not change unexpectedly.
7. As a user, I want successful sign-in retained even when model discovery fails, so I can retry selection without repeating login.
8. As a user without plan permission, I want clear guidance and a preserved sign-in, so I can enable permission or configure my own API key.
9. As an API user, I want ChatGPT credentials and API keys to coexist, so I can change routes without disconnecting either method.
10. As a user, I want terminal commands and piped input to avoid unexpected browser or picker prompts, so scripts cannot hang waiting for interactive setup.
11. As a user, I want streamed text and local Tools to work on ChatGPT, so the same agent can complete my work using my plan.
12. As a user, I want failed or interrupted exchanges to preserve retryable work, so an explicit Retry can continue without duplicating known Tool effects.
13. As a user, I want plan exhaustion to stop with `Cota atingida` and usage guidance, so I decide when to wait or select another Provider.
14. As a user, I want Resume, Fork and Compression to retain their current meaning, so using a subscription does not create a separate kind of Session.
15. As a user switching accounts, I want normalized Conversation text retained with a notice before it is sent to the new account, so I can continue deliberately.
16. As a user, I want account-bound reasoning and replay kept away from other registrations, so an account change cannot reuse another account's opaque state.
17. As a user delegating work, I want each Subagent to use the parent's selected account/model, so task identity stays stable during execution.
18. As a user, I want to disconnect ChatGPT and revoke its renewable session, so the application stops using that authorization while my API keys remain usable.
19. As a user, I want credentials excluded from context, settings, history and diagnostics, so configuration and reports can be inspected safely.
20. As a user, I want current input occupancy and its limit provenance, so I can distinguish context pressure from cumulative token use.
21. As a user, I want plan token observations without invented currency or quota figures, so missing information remains visibly unknown.
22. As a user with a mixed Run, I want earlier API costs preserved in `/usage` and `/report`, so selecting ChatGPT does not erase my API spend.

## Implementation Decisions

### D1. Existing seams and bounded scope

Retain the hand-rolled Provider Contract, `prepare_input`, the shared bounded HTTP/SSE transport, Router Tool loop, Runtime Configuration snapshots, atomic settings writer, Call Log and `InputBox`. Add a focused `chatgpt_auth` module for account lifecycle/storage and a `providers/chatgpt` implementation for Responses translation, streaming and replay. Keep account model discovery with those account-specific responsibilities; do not build a generic discovery framework. The Router receives account binding and classified failures; it does not implement OAuth or choose credentials.

Use existing stdlib networking, browser, loopback-server and process-lock facilities. Declare `PyJWT[crypto]` directly and update the dependency lock because cryptographic verification must not rely on a transitive dependency. Reuse prompt-toolkit; introduce no UI dependency, vendor SDK, Codex process or hosted service. [ADR-0015](../adrs/0015-chatgpt-subscription-provider.md) amends the catalog/authentication assumptions of ADR-0011/0012 and the bounded-output assumption of ADR-0002 for this Provider only.

### D2. Entry, admission and route selection

Separate recoverable route readiness from fatal malformed runtime/resource configuration. Missing/unknown Provider, missing model/key, missing ChatGPT session/permission, unavailable catalog or no longer admitted model must leave the interactive REPL usable with an explicit diagnostic. Invalid budget syntax, unsafe persistence or corrupt Session evidence retain their existing fatal behavior. No placeholder route is dispatched or silently saved. Initial Session/Run metadata must represent an absent or invalid selected route without fabricating a valid pair; later task openings record admitted snapshots only.

Admission occurs before every model-backed task, explicit Retry and manual Compression. Automatic Compression and transient retries use the enclosing admitted task snapshot. A usable API route requires its existing key/catalog checks. A usable ChatGPT route requires a validated registration, current plan permission, a renewable/valid session and an account-listed exact model. Connecting ChatGPT does not require Models.dev to be available. Existing API admission/capacity behavior remains intact. An expired/revoked route is shown as unready rather than relabeled as API access.

`/connect chatgpt` reuses a usable session or starts explicit local browser authorization, then fetches account choices and opens the picker. `InputBox` supplies Up/Down navigation, Enter selection, Escape cancellation and safe Ctrl-C/EOF handling. Show display names with exact slugs, in server order, after terminal-control sanitization. Never auto-select the first model. `/model chatgpt <slug>` while disconnected first offers an explicit Continue with ChatGPT choice; it does not open the browser without the user's choice. After login it validates and confirms the exact requested slug before selection. `/model openai <id>` and the other API forms retain current semantics.

Authentication and model activation are separate transactions: validated sign-in may persist first; account validation, deliberate model choice and atomic pair save must all succeed before active selection changes. Failed/cancelled login preserves the old connection and selection. Successful login survives empty models, picker cancellation and model-list failure, with next-action guidance. Failed route save preserves the earlier active pair and persisted pair. Retained Conversation text is unchanged by selection. A previously selected ChatGPT route disconnected or invalidated by an account change stays selected but unready until revalidated/explicitly selected; never run its old slug on the new account by accident.

`/models chatgpt [query]` and `personal-agent --models chatgpt [--search ...]` list the account's models, with no paid inference. They give connect guidance if unavailable and never launch login. Unqualified listing includes the ChatGPT access path without letting account/catalog failure hide other available Providers. `/models refresh` and `--refresh-models` remain Models.dev operations; `/connect chatgpt`, ChatGPT listing and ChatGPT model selection fetch current account choices. Account-list failure blocks new ChatGPT admission with guidance; already admitted tasks keep their snapshot. `/config` shows safe connection/permission/readiness status and routes to the same connect/disconnect/model actions. Do not add a separate authentication CLI or status command.

Without interactive `InputBox`, explicit exact-model commands may work with existing credentials, but commands needing login, first-use notice dismissal, a picker or connect-now choice fail promptly with local interactive guidance. No browser or modal is started for noninteractive input. This does not make ordinary API tasks require a TTY.

### D3. OAuth and registration identity

One connected account per installation; retain distinct registration metadata internally without a saved-account picker. Identify a registration by validated issuer/subject plus its issued client ID, never email. Retain the stable host ID and last registration's issued ID after disconnect. Routine reauthorization reuses that issued ID and checks the same validated identity. An explicit different-account connection uses initial dynamic registration; this can be an action in the connect flow, not a selector over saved accounts. Never silently replace a returning registration when identity differs. Settings show a safe account label sufficient to distinguish registrations with the same email.

Follow [official registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in). Bind a listener to `127.0.0.1` before opening the system browser; preserve the `/auth/callback` path, scheme and host across attempts and use the exact chosen port/URI throughout each attempt. Use a five-minute cancellable wait with listener cleanup. Generate fresh unpredictable state/nonce and PKCE S256 verifier per attempt. Reject missing, duplicate, mismatched or already consumed callback parameters and wrong callback path; invalid unrelated requests must not authenticate or disclose pending state.

Authorize at `https://auth.openai.com/api/accounts/authorize` for resource `https://api.openai.com/v1`, with `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`. Initial registration uses `dynamic_agent_client`, stable `ext_agent_host_id` and `agent_name_hint=Personal Agent`. The callback must supply a real issued `client_id`; exchange with that ID, never the dynamic entrypoint, at `https://auth.openai.com/api/accounts/oauth/token` using the form-encoded authorization code, original verifier, redirect URI and resource. Returning login omits the name hint; send any retained `id_token_hint` only to the trusted authorization endpoint, associated with that registration. After sign-out no token hint survives. Callback scope alone is not permission evidence. A spent/invalid code is discarded; restart only as a new explicit attempt using the issued registration, not repeated exchange.

Verify ID-token signature against the trusted OpenAI JWKS, with a trusted asymmetric algorithm allowlist independent of token headers, expected issuer `https://auth.openai.com`, audience containing the issued client ID, required expiration/subject and the attempt's nonce. Validate applicable time/authorized-party constraints; reject empty subject, unsupported algorithms, bad signature, expired token, wrong audience/issuer/nonce or returning-identity mismatch. Never derive JWKS endpoints from token `jku`/`iss` or trust unverified claims for identity. Validate token response shape/type, granted scopes and expiry before replacing credentials. Keep a valid identity-only sign-in if direct-plan permission is missing, mark plan use disabled and block inference. A user choosing to enable plan use explicitly repeats OAuth with full scopes and supported `prompt=consent`; do not send rollout-gated `force_reconsent` without confirmed support or repeatedly force consent for normal sign-ins. [Official recovery guidance](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery) defines this distinction.

### D4. Private session lifecycle and secret protection

Use a versioned private global record under `~/.personal_agent/chatgpt-auth.json`, separate from project/home dotenv settings and Session logs, with owner-only directory/file permissions (`0700`/`0600`), validated shape, bounded reads and atomic durable replacement. Retain host/registration metadata, one connected token set, granted permission, server expiry/refresh hints and the first-use notice acknowledgement. Reject unsafe ownership, symlinks or permissive existing credential storage rather than reading secrets through them. Failure to save credentials or rotated tokens prevents dependent inference and surfaces a safe error; never continue using an unpersisted rotated session. Store no plaintext in project files or process environment just to pass authentication between modules.

The module exposes connect, safe status, disconnect and valid-credential resolution for a pinned opaque registration reference. OAuth tokens remain private to credential resolution and transport. Use a cross-process lock, reread after acquiring it and serialize refresh/activation/disconnect with token-generation checks. A task pins registration and session generation, not an expiring access-token string; refresh rotates tokens within that generation. A stale process cannot overwrite a newer login, resurrect a disconnected session or resolve credentials for whichever account is globally active. A reference to an unavailable/replaced generation fails safely. Hold no lock while waiting for interactive browser consent.

Refresh near server-provided expiry using `earliest_refresh_at` as guidance, not a guaranteed denial boundary. Send the saved issued client ID, latest refresh token and resource to the documented token endpoint; omit scope to retain grant. Persist replacement refresh/access/ID tokens and expiry atomically; validate returned ID-token signature/identity/client/time and permission evidence before accepting it. Refresh has no new authorization-attempt nonce; do not incorrectly require a fresh login nonce on refresh. Retain the earlier grant only where the OAuth refresh contract allows omitted scope. Serialize concurrent processes so a later reader uses the newest committed credentials. Temporary network/5xx failure preserves credentials with bounded backoff; terminal refresh invalidation clears unusable tokens, retains registration metadata and asks for reconnect. Do not infer revocation from arbitrary network failure.

`/disconnect chatgpt` blocks new use of its session and attempts refresh-token revocation using the HTTPS revocation endpoint in trusted OpenAI OIDC discovery (validate issuer and trusted endpoint origin). Use form `token`, `token_type_hint=refresh_token` and issued `client_id`. Empty 200 is success, including idempotent repeat. Retry network/5xx errors with bounded backoff while the refresh token is available; then clear local access/refresh/ID tokens even if remote confirmation failed, visibly report that fact and link ChatGPT settings. Do not delete API keys, host ID, registration identity or route selection. A generation tombstone prevents another process from refreshing/resurrecting it; existing requests may finish but no new follow-up or child dispatch may use it. This does not promise cancellation of work already accepted remotely.

Redaction must include current and retired credentials learned during the Run, refresh replacement tokens, callback code/verifier/state/nonce and authorization URLs with ID-token hints. Register secrets before constructing/logging errors or delivering streamed text. Protect across split stream chunks and model/Tool echo, detailed audit, Call Log, terminal diagnostics, child IPC receipts/results and exceptions. OAuth headers, tokens, codes, hints, private credential records and raw identity claims are never model input or log evidence. Use opaque local registration references for attribution, not JWTs or email. Opaque reasoning replay is private model state, never displayed or added to prompts as instructions.

### D5. Account models and capacity provenance

Fetch `GET https://api.openai.com/v1/models` with OAuth bearer credentials for the pinned registration. Consume the SIWC `models` array, require nonempty unique exact `slug`, display text and `visibility=list`, and preserve server order. Validate/bound the response (8 MiB body and 10,000 entries maximum); malformed required structure fails visibly. Filter non-list entries. Never substitute the API-key `data/id` schema, hardcode spike models, import catalog instructions/templates, endpoints or remote configuration, or suggest that listing guarantees inference.

Account choices and any in-memory catalog snapshot are registration/session-generation bound and invalidated on disconnect/account change. Recheck choices at new-task/Retry/manual-Compression admission; no background polling or paid probe. Optional public metadata complements exact known model capacities, never admission or pricing. For ChatGPT each capacity field resolves manual exact override, explicitly documented account capacity if available, exact public Models.dev metadata, exact locked LiteLLM metadata, then labeled assumptions. An absent public catalog must not prevent assumed-capacity ChatGPT use. The current SIWC model-list contract documents slug/name/visibility, not `context_window`/`max_context_window`; do not promote those spike fields to verified limits or infer identity from model-name patterns. No lookup as `openai/<similar-name>` just to get a plausible price or capacity.

Preserve `context_budget.resolve`'s existing 16,000-token output reservation (bounded by known output allowance), configured context budget, 10,000-token margin and complete prepared-input assessment. With total T, configured budget B, optional input limit I and reserve R: effective total is `min(B,T)` and input ceiling is `min(effective total-R, I or effective total)-10,000`. A nonpositive allowance blocks dispatch. Capacity and provenance are task snapshots. For ChatGPT R is only a planning estimate; neither local truncation nor request cancellation is a guaranteed remote generation/billing cap. Do not send `max_output_tokens` on this route. Existing Providers retain their enforced output parameters.

### D6. Responses, streaming and local Tools

Use OAuth bearer credentials only with `POST https://api.openai.com/v1/responses`. Keep the existing OpenAI API-key Provider on its current endpoint/contract. Build a dedicated allowlisted SIWC request: selected slug, complete `input` array, `instructions`/developer content, `store=false`, `stream=true` and supported local Tool declarations. Translate the existing System Prompt into `instructions` rather than explicit system items. Omit all unsupported fields in [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations), including output cap, previous-response/conversation state, background, sampling and metadata. HTTP SSE only; do not call `backend-api`, use remote storage or depend on WebSocket continuation.

Map existing `ToolDef` schemas into one stable local namespace (for example `personal_agent`) and validate returned namespace/name/call ID before mapping to the existing local Tool Registry. Calls from unknown namespaces cannot alias allowed Tools. Correlate namespaced `function_call` and `function_call_output` by `call_id`, preserving namespace in replay. Preserve raw arguments for existing validation/errors. Local shell, MCP resources, skills, questions, background-job and agent Tools stay ordinary client-executed functions; do not advertise unsupported hosted Tools or Responses `tool_search`. Agent Mode, Tool Confirmation, restricted child capabilities, per-round limit and the 16-call batch ceiling remain unchanged.

Consume SSE with or without a display callback and without requiring Content-Type. Assemble ordered output items from item lifecycle events; a completion envelope with empty `output` must not discard collected items. Handle text and argument deltas, item-done snapshots, reasoning/encrypted state, message phase, usage and terminal events without double-appending duplicated snapshots. Only safe ordinary text reaches streaming output; no reasoning, arguments or encrypted content is rendered. Only one coherent `response.completed` with validated assembled items may succeed. Incomplete/failed/error events, inconsistent identity/items, malformed arguments/protocol, oversized events/aggregate response or EOF without completion fail safely; no Tools execute from provisional/rejected output. Preserve existing 256 KiB event and 8 MiB assembled-response bounds. Use termination classification to keep incomplete output provisional, never a completed answer.

### D7. Failures, Retry and usage evidence

Classify both HTTP failures and SSE errors after HTTP 200, including `error` followed by `response.failed`, once per physical Attempt. Keep safe HTTP status, structured code/parameter and request ID; handle nonstandard `detail` diagnostic shapes without inventing machine codes. Do not double-charge/double-log a single failed stream. Carry observed valid usage into failed/interrupted Attempts and preserve missing counters as unknown.

`subscription_sharing_usage_limit_exceeded` immediately stops this execution's further plan inference, Compression and child dispatch; display `Cota atingida`, Manage usage and explicit wait-or-select-another-Provider-then-`/retry` guidance. No automatic sleep, fallback, OAuth loop or guessed reset. A later explicit Retry is a user decision to attempt the currently admitted route again; it retains pending prefix, original ordinal and a new execution identity. Unrelated HTTP 429s must not automatically be labeled plan exhaustion.

`context_length_exceeded` uses existing one-shot same-route overflow Compression only when complete input can strictly shrink under the ceiling; no recursive summary recovery. Unsupported capability/route, policy/permission and ineligibility are nontransient errors with corrective guidance. Temporary infrastructure/usage-unavailable 503 and supported transport failures use the existing bounded same-route transient budget/backoff. Authentication or terminal refresh errors require explicit reconnect after checking/reloading the pinned session; never endlessly retry stale credentials or launch a browser from inference. Missing permission never runs inference.

Normalize observed input/output, cache-read and reasoning token details from Responses without double-counting included cache/reasoning subsets. Store `cost=null` and `cost_estimated=false` for ChatGPT Attempts, including failures, Compression and child work; never call API pricing estimation for this Provider. Optional invalid counters are marked invalid/unknown without inventing zero or silently upgrading other measurements. Do not add quota polling or derive remaining percentages/reset times from observed consumption.

### D8. Durable Conversation and account-bound replay

Extend existing Call Log v3 additively, preserving existing v3 API Sessions and refusing pre-v3 formats unchanged. Run metadata, task/Retry openings and Attempts carry access method (`api_key` or `chatgpt_plan`) and, for ChatGPT, opaque registration reference. Task/child snapshots also include a session generation for safe credential resolution; credentials are never persisted in the Call Log. An absent/invalid route at entry is representable as readiness evidence, not a fabricated admitted route. Preserve ordinary execution identity, submission attribution, checkpoint/recovery and fatal-write behavior.

Use the existing `AssistantMessage.replay` and Provider replay preparation/rebase hooks for versioned Responses items. Persist a validated replay envelope on successful Turn Ends and pending continuation, bound to `chatgpt`, exact model and registration reference. Keep normalized user/assistant/Tool content as the portable Conversation. A ChatGPT pending continuation uses its own validated version/schema; continue reading existing version-1 Gemini/API pending continuations unchanged. Reject malformed ChatGPT binding/envelope/item graph before Resume append. Do not migrate or rewrite old Sessions or loosen Gemini validation to accept arbitrary JSON.

Replay preserves ordered encrypted reasoning, assistant message phase and function call/result correlation at a complete balanced exchange boundary; validate its correlation to normalized messages, consumed-prefix indices and active-history boundaries. No unexecuted provisional Tool call becomes a completed/pending result. Mid-batch interruption retains actual results and explicit interrupted/not-executed outcomes under the existing continuation rules. Opaque replay must not make a Tool run again merely because a Session was resumed.

Same-model/same-registration continuation can reuse opaque replay after current session authorization; a refreshed/reauthed session for the same validated registration may reuse it. Different Provider, model or registration uses normalized messages with all incompatible opaque items removed. Account changes never clear portable Conversation text or Summary. Before the first request that would send existing normalized Conversation/Summary/pending text to a different ChatGPT registration, show an explicit notice naming the safe new account label; emit it before dispatch on normal submission, Retry, Resume, Fork and Compression paths. This notice is not an extra approval requirement; the user's selected account/route and explicit task remain the authorization. Remember the last destination registration through durable provenance so restarting cannot suppress the notice. Noninteractive mode may print this notice before an explicitly requested, already authorized dispatch.

Completed same-route Conversation replay survives Resume and Fork. Fork copies allowed bound replay and provenance into the child Session, retains parent linkage/empty spend and retains existing pending-turn refusal. Compression receives complete supported context on the pinned route; its saved Summary replaces compressed turns and retires their opaque items while retaining the two recent turns with correct replay rebasing. Compression output stays internal. `/clear`, Undo and File recovery invalidate/rebase replay and pending state consistently with their current Conversation semantics. No session command resolves opaque items from another account.

### D9. Subagent inheritance

The child Runtime Configuration serializes the parent's exact Provider/model, access method, registration reference, session generation and capacity snapshot; it never adopts a different installation's currently active account and never serializes OAuth tokens as API keys. Resolve valid credentials inside each process under the shared session lock. Rotation for the same generation is allowed; disconnect/account replacement blocks new child/follow-up inference instead of retargeting. Apply dynamic secret protection to parent and child streams, IPC and receipts. The parent route stays fixed even if another REPL changes selection/account.

Preserve isolated child Sessions/Call Logs, one active child, narrowed Tools, parent Agent Mode/confirmations, linked attribution, cancellation/job cleanup and fatal evidence propagation. Receipts and reconciliation carry access method/registration and token observations; deduplicate each physical child Attempt once. ChatGPT children contribute plan observations with unknown currency, while API children retain current spend aggregation. Failed/exhausted child work returns a handoff without fallback or automatic resumption. Propagate child plan exhaustion so the parent also stops further inference on that pinned plan during the current execution, preserving pending evidence rather than requesting a synthesis from the exhausted route.

### D10. Footer, context occupancy, usage and reports

Footer content derives from the selected route, not merely the presence of a connection. Use existing compact style and sanitized labels. API routes show `API key`, estimated current input occupancy/effective input allowance and current Run API spend with reported/estimated/unknown coverage. ChatGPT routes show `Assinatura ChatGPT`, occupancy and `/usage`; omit a monetary counter even when earlier API spend exists. Missing/invalid/disconnected routes show unconfigured/unready state and unknown occupancy, never ready-looking placeholders. Plan exhaustion shows `Cota atingida` until explicit retry/route change clears or replaces that failed readiness state.

Occupancy uses the latest complete input assessment for the active task snapshot: System Prompt/instructions, Tool schemas, Conversation/Summary, project instructions, active Skills, Memory, Todos and actual results, including replay's model-facing contribution. It is input tokens over D5's effective input ceiling, not cumulative tokens divided by total context. Show `~` for estimates and an explicit assumed/manual/public provenance cue; absent assessment is unknown, not zero. New route/context configuration, Resume/Fork, clear/Undo or Compression invalidates/recomputes stale assessment. Do not estimate full input from only visible task text or invent a precise token count for encrypted content; use the established conservative serialization estimator with disclosed limitations. Route admission/capacity resolution may provide allowance before a task exists, but not fabricated occupancy.

`/usage` separates Run API-cost totals (including earlier routes and child API Attempts) with reported/estimated/unknown coverage from observed ChatGPT plan input/output/cache/reasoning details (including failed/Compression/child Attempts) with independent missing/invalid coverage. Show `Manage usage: https://chatgpt.com/settings/usage` and unknown plan monetary cost. Do not present API subtotal as a complete mixed-provider cost. Keep Session Report's bounded Run/execution/purpose/route grouping and independent sample coverage; distinguish access methods/registrations without exposing identities, preserve historical API prices and count linked children once. Plan costs remain unavailable, never `$0`, API-equivalent price or implied free billing; known API-only subtotal may legitimately be zero with its own scope.

After first successful permission-enabled login, show one dismissible terminal notice per registration explaining that eligible requests use the user's ChatGPT plan and providing Manage usage. Use Continue with ChatGPT for the login action. Record acknowledgement privately so subsequent launches/reauthorization do not repeat it; no inference before that first notice is acknowledged. `/config` and `/usage` retain a visible way to manage usage. Ineligible/missing permission status provides existing API configuration as an explicit alternative, never a fallback. No remaining quota, reset time or independent app allowance is invented.

## Testing Decisions

Use the highest existing observable seam: CLI/REPL with real settings/temporary storage and fake browser/OAuth/model/SSE responses; Router with actual Provider request serialization and stubbed shared transport; real Call Log writer/reader across Resume/Fork; Subagent's process seam with synthetic workers. Assertions inspect emitted requests, visible output, immutable route/account identity, persisted evidence and forbidden effects rather than private helper call order.

Test OAuth separately at its real boundary using temporary owner-only storage, a loopback callback, generated test RSA/JWKS and an injected trusted-transport stand-in. Cover every signature/state/nonce/identity/scope failure, cancellation/deadline, unsafe storage, interrupted atomic replacement, refresh persistence failure and two real processes racing rotation/disconnect. No real browser authorization, accounts, credentials or paid inference are required for deterministic acceptance. Do not read spike token files or credential stores as fixtures.

Prior art: `test_main`, `test_repl`, `test_input_box`, `test_catalog_selection`, `test_direct_pair_config`, `test_runtime_config`, `test_native_streaming`, `test_provider`, `test_context_budget`, `test_preventive_compression`, `test_context_recovery`, `test_continuation`, `test_call_log`, `test_fork`, `test_subagents`, `test_detailed_audit` and `test_session_report`. Add focused synthetic ChatGPT auth/protocol fixtures rather than modifying the default four-Provider catalog to pretend ChatGPT is Models.dev-admitted. Snapshot the unchanged canonical prompt/Tool surface where integration could alter it; Responses serialization is tested separately.

Required adversarial streams include split secret fragments, text then failed/error terminal, empty completion output with item-done data, multi-Tool/unknown namespace, malformed/oversized events, truncated UTF-8/EOF, duplicated terminal usage and incomplete output. State tests combine API → ChatGPT → API, same registration reauth, different registration with identical email, account switch between parent and child dispatch, and plan exhaustion after a completed Tool batch. Verify all current Providers retain admission, enforced output limits, replay, cost and prompt-cache behavior.

Each ticket runs focused tests before the full `.venv/bin/pytest -q` suite. No production implementation, live login or live inference is authorized by this planning handoff. After later implementation authorization, an optional explicitly authorized real-account smoke check can confirm local login/model discovery/text/Tool/refresh/revocation with available quota; deterministic checks must already establish the contract and a listing alone is not proof of successful inference.

## Out of Scope

Shared maintainer credentials, hosted account service, saved-account selector, SSH/headless login, credential import/transfer, external authentication CLI/status commands, automatic Provider fallback, automatic quota waiting, quota estimates, API-equivalent plan pricing, vendor agent SDK execution, WebSocket optimization, hosted Responses Tools, multimodal feature expansion, old-format Session migration and whole-codebase refactors.
