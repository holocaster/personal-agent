# 0034 — MCP Resources

Brief: `docs/briefs/0034-mcp-resources.md`. Vocabulary: `docs/CONTEXT.md`.
ADR-0002 governs Providers, not this MCP client; ADR-0005 governs unchanged Call Log replay.

## Problem Statement

The agent cannot use context exposed by a user's local MCP server during a routed task.

## Solution

Configure one local server and let the model request resource discovery and text reads through three explicit Tools. Plan and build confirm every operation before launching the server; auto executes validated operations without prompting. Results are bounded, attributed, untrusted Tool content.

## User Stories

1. As a user, I want to opt in to one server, so that its context becomes available intentionally.
2. As a user, I want an unconfigured installation to launch nothing, so that ordinary runs need no MCP setup.
3. As a user, I want malformed configuration reported before a task, so that mistakes are actionable.
4. As a user, I want the model to list Resources, so that I need not name each URI manually.
5. As a user, I want the model to list Resource Templates, so that it can construct relevant resource URIs.
6. As a user, I want text read from a chosen URI, so that the model can answer using external context.
7. As a user, I want the configured server and operation visible at confirmation, so that I know what I approve.
8. As a user, I want the read URI included in confirmation, so that approval identifies the requested context.
9. As a user, I want rejection to prevent even server startup, so that a denied call has no process effects.
10. As a user, I want auto to use these operations without prompts, so that it follows my selected Agent Mode.
11. As a user, I want the command controlled by configuration, so that model arguments cannot select another process.
12. As a user, I want large results visibly shortened, so that server output does not dominate the Conversation.
13. As a user, I want unsupported binary content and server failures reported, so that missing context is not presented as success.
14. As a user, I want server processes cleaned up after calls and interruptions, so that operations do not leave background servers running.
15. As a user, I want normal Tool display and Call Log records, so that these operations remain visible and resumable.
16. As a user, I want the host-access boundary documented, so that I do not mistake a local server for a workspace sandbox.

## Requirements

- **R1 — Opt-in configuration.** Read `PA_MCP_SERVER` after existing dotenv loading at Run startup. Unset or whitespace-only means disabled. Otherwise it is one JSON object with required `name` (1–80 characters, nonblank), `command` (nonblank executable name or path), optional `args` (array of strings, default empty), and no other keys. Reject wrong types, missing fields, unknown fields, and NUL characters with a configuration error before entering the REPL; do not echo the raw configuration or arguments in errors. Capture the validated configuration for the Run. Launch by argument vector without shell parsing or interpolation, from Workspace Root. Use the SDK's minimal default environment allowlist: on POSIX only available `HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM`, and `USER` values are eligible for inheritance (subject to SDK filtering). Do not pass the whole parent environment or add Provider/API keys or other environment overrides. Configuration may use a user-owned executable wrapper if custom environment is needed. The model cannot supply server selection, command, arguments, environment, or cwd.
- **R2 — Three explicit Tools.** When configured, register `mcp_list_resources`, `mcp_list_resource_templates`, and `mcp_read_resource` in all three Agent Modes. The two list schemas accept only `{}`; read requires only `uri`, a nonblank string of at most 4096 characters with a URI scheme and no control characters or unexpanded template braces. All schemas reject additional properties. Send the validated URI to the configured server; do not interpret it as a workspace file or fetch it directly. Reading does not require a prior list result, since template-generated URIs may not be listed. When disabled, omit all three definitions and reject direct calls by name without launching anything. No dynamic MCP Tool discovery or registration.
- **R3 — Per-call confirmation.** Reuse validation → prepare → confirmation → apply. Preparation performs local validation only. In plan and build every valid operation requires the existing Tool Confirmation, identifying configured server name and operation, plus full URI for read. Rejection, missing confirmation callback, EOF, and interruption before approval start no process and send no request. Auto skips that prompt only after validation. Approval covers that operation's protocol negotiation and bounded pagination, never later Tool calls. Keep the routed turn's existing fixed mode semantics.
- **R4 — Protocol and lifecycle.** Each approved call creates one stdio connection, negotiates MCP using the v2 Client's default `mode="auto"`, verifies server Resources capability, executes its requested resource operation, and closes the connection/process before returning. List calls can issue bounded continuation requests within that connection (R5). The SDK sends `server/discover` for protocol 2026-07-28 and falls back to the legacy `initialize` handshake for older servers; allow this negotiation within the same approved call. This SDK protocol mode is independent of Agent Mode. No connection pool, background server, application-level retry, or persistent cursor. Use a 30-second deadline for startup, protocol negotiation, and operation together, followed by bounded cleanup (at most 5 seconds before forced termination and reaping of the launched process). Success, protocol/server error, timeout, and Ctrl-C all clean up; Ctrl-C retains the existing interrupted-turn behavior. A subsequent call may start a fresh process. Do not advertise/implement sampling, elicitation, roots, or any server-driven user interaction; unsupported server requests and modern `InputRequiredResult` responses must yield an ordinary unsupported-interaction Tool error without invoking a Provider, requesting user input, or retrying with an answer. SDK-required protocol bookkeeping is permitted.
- **R5 — Bounded discovery.** Map the list Tools to `resources/list` and `resources/templates/list`. Follow server cursors only inside the approved operation, preserving response order, stopping on exhaustion, 100 entries, 10 pages, repeated cursor, deadline, or output limit. Return `{server, resources, truncated}` or `{server, resource_templates, truncated}`; items include `uri` or `uriTemplate`, `name`, and optional `description`/`mimeType`. Discard other metadata. Set `truncated: true` whenever entries or pages are omitted; do not imply the returned catalog is exhaustive. Empty catalogs are successful. No cursor is exposed to the model. Truncate optional descriptive text or omit entries to stay within R7; never shorten an emitted URI/template into a different identifier.
- **R6 — Text reads.** Map read to `resources/read`. Return `{server, uri, contents, truncated}`, with ordered text items `{uri, mimeType?, text}`. Preserve returned item URIs as provenance even when different from the requested URI. Accept text contents regardless of MIME label. Do not decode blobs or embed binary/base64 data: any blob item makes the operation an explicit unsupported-content Tool error, including mixed text/blob responses. Empty contents are successful. Omit unsupported metadata; shorten text on UTF-8 boundaries and omit later items as necessary under R7, setting `truncated: true`. Never silently rewrite a URI.
- **R7 — Output and errors.** Cap each MCP Tool result content at 32 KiB measured as UTF-8 JSON with `ensure_ascii=False` and default JSON separators, including provenance, metadata, truncation flags, and errors. This fixed MCP cap is independent of `PA_MAX_READ_BYTES`. If required provenance alone cannot fit, return a bounded Tool error. Normalize missing executable, protocol-negotiation/capability failures, disconnect, malformed response, timeout, missing resource, and server-reported failures into ordinary bounded Tool errors identifying server and operation. Do not dump tracebacks, raw server error data, configuration arguments, or stderr into the Conversation. Route server stderr to a sink so it cannot corrupt terminal presentation or accumulate unbounded in memory. This is a Conversation output cap, not a sandbox or a guarantee limiting the SDK's incoming wire allocation.
- **R8 — Integration and trust.** Use existing Tool result presentation, Conversation messages, Call Log execution entries, and Resume replay. Identify the configured server in displayed results and error results; read results include the requested URI. Server content and metadata remain untrusted Tool data, never System Prompt instructions or newly registered capabilities. Tool descriptions/System Prompt explain availability and mode confirmation accurately. Content cannot change mode, configuration, or Tool gates. Preserve existing built-in Tool behavior and Provider contracts; do not add a log schema or persistent MCP state.
- **R9 — Configuration documentation.** Add a concise README configuration example using `PA_MCP_SERVER` with command/args, describe all three operations, per-operation process lifetime, text-only reads, list/result bounds, 30-second deadline, minimal default SDK environment allowlist (including the POSIX names in R1), disabled state, and plan/build versus auto policy. State explicitly that the local server executes under the user's account with its own host access and is not confined by Workspace Root checks on built-in file Tools. Configuring Resources operations does not make the server executable itself read-only. Do not present this as sandboxing.

## Implementation Decisions

- Keep MCP functionality in one cohesive `tools` module, with configuration and prepared operation values held locally. Wire startup registration through the existing entry point and Tool Registry. Reuse the prepared Tool preview interface; add these names to plan's allowed set. Avoid a generic plugin/transport framework or Router-wide async conversion.
- Use the official Python `mcp` SDK, current stable v2 API (`mcp>=2,<3`); resolve and lock a compatible stable release at implementation time. No v1 compatibility constraint exists in this Python 3.12+ repository. Use public `Client` with `StdioServerParameters` and `stdio_client(..., errlog=...)` for the stderr sink, context-managed with default protocol `mode="auto"`. It handles framing, modern discovery/legacy initialization and typed results; use its `list_resources`, `list_resource_templates`, and `read_resource` methods and adapt v2 result fields to R5–R6. Bridge the synchronous Tool apply boundary with one short-lived async execution per call and context-managed transport/client ownership. Confirm the selected SDK's shutdown behavior and implement bounded termination only where it is insufficient. This is not a Provider SDK and does not change ADR-0002.
- Reuse existing Tool and REPL boundaries for tests. One additional external boundary is the launched stdio process; a deterministic local fixture server makes its effects observable without credentials, network, or a real model.
- No new ADR: the brief settled transport, server count, capability and approval scope; lifecycle and bounded defaults are planner-owned details.

## Testing Decisions

Test observable requests, launch records, child exit, prompts, Provider-visible messages and logged results, rather than private SDK calls alone. Use existing `tests/test_websearch.py`, `tests/test_agent_mode.py`, `tests/test_main.py`, `tests/test_routing.py`, and scripted `run_repl`/fake Provider patterns as prior art.

- Startup/Registry: valid and invalid configuration, disabled/reconfigured registration, exact schemas, custom URI schemes, invalid calls before prompt/launch, no model command override, the minimal child environment (a sentinel parent secret is absent), and definitions in all modes.
- Script a routed task that lists Resources, lists Templates, constructs a template URI and reads it. Assert only SDK negotiation (`server/discover`, or its legacy initialization fallback) and allowed resource methods reach the fixture; no MCP Tools, prompts, sampling, or local filesystem dispatch. Confirm each plan/build call independently, exercise reject/EOF/missing callback, and auto without approval input.
- Cover paginated/empty lists, repeated cursors and page/item limits; large descriptions, multibyte text, multiple read items, oversized identifiers and metadata, blobs/mixed content. Measure final serialized content against the exact R7 cap and verify provenance/truncation.
- Exercise a missing command, missing Resources capability, server error, malformed reply, early exit, hung discovery/initialization, hung operation, and Ctrl-C. Assert launched child exits on each path, a denied call creates no launch marker, and another approved call still succeeds. Exercise modern negotiation, SDK fallback with a legacy fixture, and unsupported modern input-required responses without any host action or retry. Shorten deadlines via a test seam rather than waiting 30 seconds per test.
- At the REPL seam assert confirmation identity/URI, normal success/error display, Tool result delivery to the fake Provider, Call Log/Resume content, and untrusted instruction text never bypassing runtime gates. Check built-in plan/build/auto policy regressions. Run the full offline pytest suite once integration is complete.

## Out of Scope

MCP Tools (including read-only Tools), remote HTTP, multiple servers, OAuth, plugin installation, automatic discovery, subscriptions/list-change refresh, resource completion, binary rendering, template expansion utilities, caching, persistent connections, configuration editing commands, and a process sandbox.
